## 問題描述

`_charge_list_rows` 同 `_charge_track_field` 用 `raise ValueError(...)` / `raise RuntimeError(...)`
表達「呢個 request 超咗 budget」。Strawberry 將任何由 resolver 掟出、而唔係
`GraphQLError` 子類嘅 exception 當成**未預期錯誤**，經 `strawberry.execution` logger
以 `ERROR` level 連同 `exc_info` 記落去。

即係話：**一個完全喺預期之內、由設計明確要求發生嘅拒絕，被當成 server 出事咁記錄。**

## 影響

**回俾 client 嗰面係乾淨嘅**（QA 已核實，唔使改）：response 只有一句
`"list row budget exhausted: one request may read at most 4000 rows"`，
冇 context key 名、冇 traceback、冇路徑。問題純粹喺 server log 嗰面。

1. **資訊洩漏（低強度）**：部署 log 寫低絕對檔案路徑、目錄佈局同 Python / 套件版本路徑。
   Vercel function log 由 dashboard 睇得到。
2. **Log 量放大（呢個先係實際成本）**：觸發成本係 **998 token 一個 request、public
   read-only endpoint、唔使認證**（CUI-0027 票上量過）。即係話任何人可以用極低成本
   令 log 每秒堆幾十個 10-frame traceback。呢個係 CUI-0027 特登要擋嘅嗰種放大，
   只不過搬咗去 log 嗰一層。
3. **Signal 溝淡**：`ERROR` + traceback 本來應該代表「要人去睇」。而家最常見嘅 `ERROR`
   會係一個**設計上正常**嘅拒絕，真正嘅 500 反而埋沒喺入面。

## 建議方向（由 developer 判斷）

| 方案 | 做法 | Trade-off |
|---|---|---|
| **A（推薦）** | 掟 `GraphQLError`（或者一個繼承佢嘅 `BudgetExceededError`）代替 `ValueError` | Strawberry 唔會當佢係未預期錯誤，唔會 log traceback；client 見到嘅 message 一模一樣。⚠️ 要核實 `test_a_budget_fails_closed_*` 嗰六條 param 仍然紅得起 —— 佢哋 assert `result.errors` 同 `NOT_SEEDED in message`，換 exception type 唔應該影響，但要實測 |
| B | 為 `strawberry.execution` logger 加 filter，濾走 budget 嗰類 | 唔改語意，但 filter 靠 message 字串匹配，好脆 |
| C | 唔改 | 留低一個零成本、免認證嘅 log 放大面 |

⚠️ 注意 `RuntimeError`（budget 未 seed）**應該**繼續 log traceback —— 嗰個真係 server
設定出事。只有 `ValueError`（budget 用完）先係正常拒絕。兩者要分開處理。
