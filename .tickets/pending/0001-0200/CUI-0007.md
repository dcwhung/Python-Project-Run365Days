## 問題描述

CUI-0001 修好咗 `src/export/records.py` 嘅 `_round()`（由 `value != value` 改為 `math.isfinite()`，
令 ±inf 同 NaN 一樣被處理）。

但 `src/dashboard/builder.py:22-31` 嘅 `_num()` **有一模一樣嘅缺口**：佢用 `math.isnan()` 篩選，
±inf 直接通過。

`_num()` 塑造**每一行 track point**，所以一個 inf 嘅 elevation / speed / lat 仍然會令
`write_static_json` 崩潰，而 `write_sqlite` 就會存低 `Infinity` —— **正正就係 CUI-0001 嗰個
「兩個部署目標對同一份輸入產生唔同結果」嘅分歧，只係低一層。**

## 可達性

**目前唔可達**：所有 track point 數值都經 `optional_float()`（W-005 已加 `isfinite` 檢查），
而 lat / lon 喺 CUI-0001 已經硬化。所以呢個係**硬化缺口**，唔係現行資料損壞。

## 為何獨立開票

Developer 明確指出：佢為咗避開呢個缺口，**要削弱自己嗰個 writer parity 測試** ——
呢件事本身就係應該開票嘅理由。一個測試要繞路先過到，代表被繞開嗰度有嘢未修。

`src/dashboard/` 唔喺 CUI-0001 嘅 lane scope，所以冇掂。

## 建議修復方向

1. `_num()` 由 `math.isnan()` 改為 `math.isfinite()`，同 `records.py` 嘅 `_round()` 對齊
2. 順帶考慮：`_num()`（`builder.py:22`）同 `_round()`（`records.py:64`）本身就係
   AU-024 列咗嘅重複 helper。修呢張票係將兩者收歸 `src/common/numeric.py` 嘅好時機
3. 將 CUI-0001 個 writer parity 測試恢復到未被削弱嘅版本

## 驗證方式

- 造一個 track point 帶 inf elevation / speed 嘅 records，兩個 writer 都成功且數值一致
- 365 個真實檔案 export 後 static JSON 仍然 byte-identical（6,857,102 bytes / 370 files，只差 `generated_at`）
- 209 條現有測試全綠
