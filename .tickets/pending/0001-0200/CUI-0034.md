## 問題描述

CUI-0025 整張票嘅賣點係「一個契約，兩個 mode」。個契約嘅數字 `1000` 喺 repo 入面有三份：

| # | 位置 | 形式 |
|---|---|---|
| 1 | `src/api/schema.py:31` | `MAX_TRACK_POINTS = 1000` |
| 2 | `frontend/schema.graphql:22` | SDL description 入面嘅 `(1-1000)`，由 #1 產生 |
| 3 | `frontend/src/data/static/source.ts:39` | `export const MAX_TRACK_POINTS = 1000;` |

Reviewer 喺 S-062 講「冇任何嘢令佢哋唔同步時紅」。**QA 實測之後要收緊呢句：#3 其實有被釘住，
但係被釘住嘅方式令個問題變成單向。**

## 實測（scratch copy，repo 零改動）

### 方向一：改 TS 常數 → **紅**

喺 `frontend/` 嘅 scratch copy 將 `MAX_TRACK_POINTS` 由 `1000` 改成 `999`，跑 `vitest run`：

```
Test Files  1 failed | 21 passed (22)
     Tests  3 failed | 128 passed (131)

× static source > refuses points: 0 the way api mode does ...
  → expected to throw error including 'points must be between 1 and 1000, go…'
                             but got 'points must be between 1 and  999, go…'
× static source > refuses points above the maximum api mode allows
× static source > refuses a non-integer points, which downsample has no defined answer for
```

三條測試（`source.test.ts:73` / `:78` / `:86`）即刻紅 ✅。

### 方向二：改 Python 常數 → **最終綠，而且分歧**

但釘住佢哋嘅係**三個寫死字面量**：

```ts
await expect(src.track("a", 0)).rejects.toThrow("points must be between 1 and 1000, got 0");
await expect(src.track("a", 1001)).rejects.toThrow("points must be between 1 and 1000, got 1001");
await expect(src.track("a", 2.5)).rejects.toThrow("points must be between 1 and 1000, got 2.5");
```

呢三個字面量同 `src/api/schema.py` **冇任何關係**。所以：

1. 改 `src/api/schema.py` 嘅 `MAX_TRACK_POINTS` → `run365-schema --check` 紅（唯一一個 gate）
2. 跟手 `run365-schema` 更新 `frontend/schema.graphql` → gate 綠返
3. TS 常數同三條測試仍然係 `1000` → 前端全綠
4. **收工：Python + SDL 講一個數，static mode 守另一個數，兩個 mode 契約靜靜哋分裂，所有 gate 綠**

即係話 CUI-0025 個賣點（「一個契約」）嘅唯一副本，
喺**由 Python 去 TS 呢個方向**上冇 gate。

> 📌 呢個正正係 review 報告自己喺 **S-065** 標出嚟嘅形態：
> 斷言釘住一個**字面量**而唔係釘住**真正嘅來源**。同一個 batch 入面出現兩次。

## 影響範圍

- **今日零正確性風險**：三份都係 `1000`。
- 風險係**下一次改個界**。而個界本身就係 CUI-0025 新引入嘅（static mode 之前根本冇上界），
  所以呢個復發通道係本票造出嚟嘅。

## 建議修復方向（由 developer 判斷）

- **方案 A（S-062 方案 A，推薦）**：加一條前端測試，由 `frontend/schema.graphql`
  （已經 in-repo、已經由 `run365-schema --check` 保證同 Python 同步）parse 返
  `Activity.track` description 入面嘅 `(1-N)`，assert `N === MAX_TRACK_POINTS`。
  咁條鏈就變成 Python → SDL（run365-schema gate）→ TS（新測試 gate），全程有 gate。
  Trade-off：要喺前端 parse SDL 文字，但個檔案本來就喺 repo，而且 CUI-0025 啱啱把個範圍放咗入去。
- **方案 B（順手）**：三條既有測試唔再寫死 `1000`，改用
  `` `points must be between 1 and ${MAX_TRACK_POINTS}, got 0` `` ——
  但**單獨做方案 B 會令情況變差**：方向一嗰三條測試會唔再紅，變成兩邊都冇 gate。
  **方案 B 只可以連同方案 A 一齊做。**
- **方案 C**：由 codegen 產生一個常數檔。成本遠高於收益（S-062 已評）。

## 驗證方式
