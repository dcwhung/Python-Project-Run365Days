# CUI-0018 hourly 風速讀取：`-1` sentinel 而家係「靠意外先啱」，一次 refactor 就會靜默出錯

**狀態**：pending
**類型**：bug（latent，現行行為正確）
**優先級**：🟡 Medium
**來源**：CUI-0017 修復過程中由 Backend Developer 申報，Main agent 實測確認
**建立日期**：2026-09-14

## 問題描述

`src/weather/collectors/hourly.py:112`：

```python
wind_kmh=to_float(wind_text[wind_text.find("°") + 1 :].replace("Variable at ", "")[:-5])
```

freemeteo 個風速欄有**兩種 form**，而呢句靠 `-1` sentinel 同時應付兩種：

| 輸入 | `find("°")` | 切片由 | 結果 |
|---|---|---|---|
| `N° 20 Km/h` | `1` | `2` | `" 20 Km/h"` ✅ |
| `Variable at 20 Km/h` | **`-1`** | **`0`** | `"Variable at 20 Km/h"` → 之後 `.replace()` 掃走前綴 ✅ |

**第二 form 根本冇 `°`。佢之所以 parse 得到，純粹因為 `-1 + 1 == 0`。**

即係話：**`-1` sentinel 喺呢度係 load-bearing** —— 唔係一個潛在 bug，而係一個現行正確但建立喺意外之上嘅實作。

## 同 CUI-0012 / CUI-0017 嘅關係

呢個係同一機制（`str.find()` 返 `-1` 被當成合法索引）嘅**第四個實例**：

| # | 位置 | 狀態 |
|---|---|---|
| 1 | `warnings.py` marker | ✅ CUI-0012 已修（曾靜默 scrape 錯資料） |
| 2 | `hourly.py` script 切割 | ✅ CUI-0017 已修 |
| 3 | `warnings.py` `src.rfind` | ✅ CUI-0017 已修 |
| **4** | **本票：wind `find("°")`** | **未修，而且 sentinel 係 load-bearing** |

前三個係「搵唔到會出事」。呢個相反 —— **「搵唔到」正正就係其中一條正常路徑**，只係從來冇人寫明。

## 額外風險：有測試正喺度釘住呢個意外

`test_reads_the_wind_speed_from_the_variable_direction_form` 而家係綠嘅，但佢釘住嘅係
「`-1 + 1 = 0` 令切片由頭開始」呢個副作用，而唔係「兩種 form 各自點處理」呢個意圖。
所以任何人將 `find()` 換成一個更「安全」嘅寫法（例如加 guard 令搵唔到時回 `None` 或 skip），
**會即刻打爛 Variable form**，而測試會紅得莫名其妙。

## 建議修復方向

明確寫出兩個 case，唔好再靠算術：

- 用一個 regex 同時覆蓋兩種 form（`(?:(?P<bearing>\w+)°\s*|Variable at\s*)(?P<speed>[\d.]+)\s*Km/h`），
  match 唔到就明確回 `None` + WARNING
- 或者先判斷 `"Variable at" in wind_text` 分兩路處理

⚠️ 修嗰陣**必須同步改寫嗰條測試**，令佢斷言「兩種 form 各自 parse 到正確速度」而唔係釘住切片行為。
同 AU-048 更新 `TestParseDateTimeWallClockUnchanged` 係同一個情況。

## 順帶（F-2，可一併做）

同一個 function 用位置切片剝單位：`[:-5]`（Km/h）、`[:-2]`（°C）、`[:-1]`（%）。
唔係 sentinel bug，但屬同一家族「假設形狀」嘅讀法，單位一改就靜默出錯。

## 驗證方式

- 兩種 wind form 各有測試，斷言**速度數值**而唔係切片結果
- 第三個 case：兩種 form 都唔符 → 明確 `None` + WARNING
- 三個 collector 覆蓋率維持 **100%**
- static JSON 仍然 byte-identical（6,857,102 bytes / 370 files）
