## 問題描述

`src/cli/collect_weather.py:26-31` 嘅 `_write_jsonl()` 寫 `record.__dict__`，即**dataclass 欄位名**。
但 `src/export/records.py:140-152` 嘅 `daily_weather_record()` 讀嘅係**舊 scraper 欄位名**。

三方對照（全部實測）：

```
已 commit 嘅 data/raw/weather/hko_daily_weather_extract.json 用嘅 key：
  ['Date', 'Max. Temp', 'Avg. Temp', 'Min. Temp', 'Humidity (%)',
   'Total Rainfall (mm)', 'Avg. Wind Speed (km/h)',
   'Sunrise', 'Solar Noon', 'Sunset', 'Moonrise', 'Moon Transit', 'Moonset']

collector 而家會寫出嘅 key（record.__dict__）：
  ['date', 'mean_temp_c', 'max_temp_c', 'min_temp_c',
   'mean_humidity_pct', 'total_rainfall_mm', 'mean_wind_kmh']

exporter 讀嘅 key：
  row["Date"]                              ← bracket access
  row.get("Max. Temp") / ("Avg. Temp") / ("Min. Temp")
  row.get("Humidity (%)") / ("Total Rainfall (mm)") / ("Avg. Wind Speed (km/h)")
  row.get("Sunrise") / ("Sunset")
```

## 比原報告更嚴重

Developer 報告話重新採集之後 exporter 會「讀成全部 `None`」。**實際會更早死**：
`records.py:143` 係 `row["Date"]` —— **bracket access 而唔係 `.get()`**，
所以第一行就 `KeyError: 'Date'`，成個 export 立即中止，唔會行到 `None` 嗰步。

另外 `Sunrise` / `Sunset` 兩個 exporter 會讀嘅欄位，`DailyWeather` dataclass **完全冇宣告** ——
即使改好 key 命名，呢兩個欄位仍然會永遠係 `None`（同 AU-037「`SunMoon` 有 model 冇 collector」係同一個斷層）。

## 可達性

**目前唔可達，但唔係因為代碼啱** —— 只係因為 `data/raw/weather/*.json` 呢批已 commit 嘅檔案
**早於呢次 rewrite**，仍然帶住舊 scraper 欄位名。

即係話：**呢條 pipeline 而家行得到，純粹因為冇人重新採集過資料。**
任何人跑 `run365-weather` 之後再跑 `run365-export`，就會即刻炸。

同樣 mismatch 亦見於 hourly 同 warnings 兩條路徑。

## 相關

呢個係 **CUI-0010 發現嘅第二件事**。第一件（`hko_daily.py` 傳 `avg_temp_c=` 而 `DailyWeather`
宣告嘅係 `mean_temp_c`，令 `run365-weather --source hko-daily` 完全跑唔到）已經喺 `5569155` 修好。
兩者根源相同：**collector 層同 export 層之間冇任何 contract，而 collector 層長期零測試（0% coverage）
所以冇人發現佢哋已經漂移。**

## 修復方向：**方案 C（用戶已拍板 2026-09-14）**

喺 collector 層同 export 層之間建立**明確 contract**，而唔係將其中一邊遷就另一邊。

### 為何唔揀 A / B

- **方案 A（統一用 dataclass 欄位名）** —— 要寫 migration script 改已 commit 嘅 `data/raw/weather/*.json`。
  嗰批係真實歷史資料，動佢風險唔值。
- **方案 B（collector 寫出舊 key）** —— mapping 表會變成第二個真相，等於將今次個漂移制度化。

### 方案 C 要做嘅嘢

1. **`src/weather/models.py` 三個 dataclass 各加一對 `to_raw_row()` / `from_raw_row()`**
   （`DailyWeather`、`HourlyWeather`、`WeatherWarning`）。
   `to_raw_row()` 產出 scraper 欄位名（即 `data/raw/weather/*.json` 現行格式），
   `from_raw_row()` 由該格式建構 dataclass。**Scraper 欄位名嘅真相收歸 dataclass 內部**，
   唔再散落 collector 同 exporter 兩邊。

2. **`src/cli/collect_weather.py` 嘅 `_write_jsonl()` 改用 `record.to_raw_row()`** 而唔係 `record.__dict__`。

3. **`src/export/records.py:140 daily_weather_record()` 同 `src/dashboard/builder.py:111 hourly_at()`
   改用 `from_raw_row()`**，唔再逐個 `row.get("Max. Temp")` 手寫 key。

4. **`Sunrise` / `Sunset` 要有明確歸屬。** 兩者喺 `data/raw/` 同 exporter 都存在，
   但 `DailyWeather` 冇宣告。二擇其一並喺 commit body 論證：
   - 加入 `DailyWeather`（但 collector 拎唔到呢兩個值 —— 佢哋原本嚟自 `sun_moon_rise_set_history.json`，
     而該 collector 從未移植，見 AU-037）
   - 明確排除，並喺 `to_raw_row()` / `from_raw_row()` 嘅 docstring 講明點解 raw row 有而 dataclass 冇

5. **Round-trip 測試（本方案嘅核心，唔可省）**
   - `from_raw_row(to_raw_row(record)) == record`（三個 dataclass 各一條）
   - 用**真實** `data/raw/weather/*.json` 抽最小樣本做 fixture，斷言 `from_raw_row()` 讀得到現行檔案
   - **End-to-end**：collector 產出（用 CUI-0010 建立嘅 fixture / socket block，唔好打真網絡）
     → `_write_jsonl` → `daily_weather_record()` 讀入 → 斷言欄位齊全且非全 `None`

   最後嗰條就係今次個 bug 潛伏咁耐嘅原因 —— 冇人測過「採集完再 export」呢條完整路徑。

### 排序約束
