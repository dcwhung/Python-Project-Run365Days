## 兩處

### 1. `src/weather/collectors/hourly.py` —— script body 字串切割

```python
script[script.find("n(") + 2 : script.find(", 'CurrentWeather")]
```

**兩個 `str.find` 都可以返 `-1`**，而 `-1` 喺 slice 入面係合法索引（尾一個字元），
所以搵唔到嘅時候唔會報錯，只會靜靜咁切出一段錯嘅字串。

**同 CUI-0012 嗰個 marker bug 完全同一類** —— `str.find()` 返 `-1` 被當成有效位置。
分別只係影響範圍窄啲：最壞情況係 `_DESCRIPTION_MAP` 查唔到而回 `"Unknown"`，
唔會好似 marker 咁 scrape 返一整批唔相干嘅 table。

CUI-0012 冇修呢處，理由充分：唔喺該票列明嘅三個位置，而且**正確修法係 parse 個 icon call
而唔係繼續切字串** —— 屬另一個層次嘅改動。

### 2. `src/weather/collectors/warnings.py` `_load_signal_metadata()` —— 無防護索引

`tds[0]` / `tds[1]` 直接索引，HKO legend table 少一格就 `IndexError`。

同 CUI-0012 修好嗰批係同一家族，但喺唔同 function，亦唔喺該票範圍。

## 可達性

兩處目前都唔可達（現行 HKO 頁面結構穩定），屬硬化缺口。

## 建議修復方向

第 1 處：**唔好再用 `str.find()` + slice**。呢個 pattern 喺本 repo 已經出事一次（CUI-0012 嘅 marker）。
用 regex 抽 `n(<key>, 'CurrentWeather'` 入面嘅 key，match 唔到就明確回 `None`
（然後 `_DESCRIPTION_MAP.get(None, "Unknown")` 自然變 `"Unknown"`，語意誠實）。

第 2 處：用 CUI-0012 建立咗嘅 `src/weather/collectors/html_reads.py` 思路 ——
先檢查 cell 數量，唔夠就 skip 該行 + WARNING。

## 驗證方式

- 兩個情境各有測試（script body 唔符預期格式、legend table 少 cell）
- 三個 collector 覆蓋率維持 **100%**
- 310 條現有測試全綠
- static JSON 仍然 byte-identical（6,857,102 bytes / 370 files）
