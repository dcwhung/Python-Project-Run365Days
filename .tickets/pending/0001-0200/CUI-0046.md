## 問題描述

S-101 修好咗 `ActivityView.test.tsx` 個 `BUDGET_MESSAGE` —— 佢 hardcode 咗 `10000`
（= `MAX_TRACK_POINTS_PER_REQUEST`，住喺 Python），而家由 SDL 反推守住。

**但同一個病喺第二個檔仲喺度**：`frontend/src/views/activities/ActivitiesView.test.tsx:13`
個 `BUDGET_MESSAGE` hardcode 咗 **`4000`**（= `MAX_LIST_ROWS_PER_REQUEST`），**冇任何守衛**。

Cleanup lane 冇郁佢，因為 S-101 只授權咗 `10000` 嗰條 —— **守範圍係啱嘅**。

## 影響

低，同 S-101 一樣：tune 個 budget 就會令呢個 fixture 靜靜哋 stale，冇任何嘢會紅。
而呢個正正係 CUI-0018 (a) 立項嘅論據（「嗰句 message 係 f-string over 常數，
tune budget 就會拆爛所有 match message 嘅 client」）。

## 建議

跟 S-101 落嘅做法（**唔好**跟原 review 報告嗰個 `readFile` 建議稿）：

1. `import schemaSdl from "../../../schema.graphql?raw"` —— 本 repo `src/data/static/source.test.ts:6`
   有先例，Vite 喺 transform 時解析路徑，唔受 runner 由邊個 directory 起步影響

   （同一句喺檔案第二處出現都會滿足 raw-text regex）
3. 比較之前先 `expect(...).not.toBeNull()`，令 description 改咗措辭會**大聲紅**而唔係靜靜跳過變假綠

⚠️ 執票前要先核實 `4000` 喺 SDL 邊一行出現、出現幾多次 —— S-101 嗰次 `10000` 喺
`frontend/schema.graphql` 只出現一次（`:22`），`4000` 未必一樣。

### 量度（票上叫核實嘅嘢，實測結果）

1. **`4000` 喺 `frontend/schema.graphql` 出現 5 次**，唔係 S-101 嗰種一次：
   `:80` `activities`、`:93` `weight`、`:103` `weather`、`:113` `warnings`、`:123` `year`。
   五句全部出自同一個 f-string `LIST_ROWS_NOTE`（`src/api/schema.py:960-965`），所以五個數字
   天生一致 —— 但「一致」唔等於「揀邊個都無所謂」：raw-text 搜尋講唔出自己搵到咗邊個 field。
   **釘死 `Query.activities`**：呢個 view 個 document 開嘅就係佢，上面 fixture 個
   `path: ["activities"]` 亦都係佢，所以佢個 description 先係呢個 fixture 應該負責嘅嗰句。
2. **兩邊確實係同一個常數嘅 f-string**：
   - runtime error message —— `src/api/schema.py:773-776`，
     `"list row budget exhausted: one request may read at most " f"{MAX_LIST_ROWS_PER_REQUEST} rows"`
   - SDL description —— `src/api/schema.py:961`，
     `f" One request may open at most {MAX_LIST_ROWS_PER_REQUEST} rows of pages in total, "`
   兩句措辭唔同，所以守衛係由 SDL 攞返個**數字**再入 TS 嗰句度比，唔係夾硬比成句。
