**同 2026-09-17 嗰個讀數一模一樣**：14 條、同樣兩個 package、同樣嘅 ID 同 fix version。
`pyproject.toml` 宣告嗰 10 個依賴仍然**零 advisory**。冇推翻票。

### 方案 A 實測

再開一個**乾淨** python 3.12 venv（同 CI 嘅 `PYTHON_VERSION: "3.12"` 一致），
按 CI 嘅次序行：`pip install -e ".[dev]"` → `python -m pip install --upgrade pip setuptools`
→ `pip install pip-audit` → `pip-audit`：

```
upgrade 前：pip 24.0、setuptools 79.0.1
upgrade 後：pip 26.2.1、setuptools 84.0.0     （fix version 係 26.2 同 83.0.0，兩個都過咗）
$ pip-audit --progress-spinner=off
No known vulnerabilities found                          exit 0
```

即係方案 A **真係修到**，唔係收埋。審嘅範圍係成個環境，實測 **65 個 distribution**。

### Scope 嘅誠實披露

`pip install pip-audit` 會將 pip-audit 自己嘅 closure（`CacheControl`、
`cyclonedx-python-lib`、`requests`、`rich` …）放埋入被審集合。呢個係「審環境而唔係審
lockfile」嘅代價，已經喺 workflow 註釋寫明：理論上有可能因為一個只有 pip-audit 需要嘅
package 而紅。今日冇。

冇用 `--strict`：pip-audit 永遠 skip `run365days` 自己（editable，唔喺 PyPI），
`--strict` 會令每一 run 都紅喺呢個永久性、設計使然嘅 skip 上。

冇加 `--ignore-vuln`（票上方案 C），冇改 `--audit-level`，冇碰 `pyproject.toml`。

### Step 位置

放喺 `lint-test` job **最尾**，同前端 audit 同一個理由（S-097）：呢道 gate 預期係因為
上游新出 advisory 而紅，唔係因為個 PR 做過乜；擺前面會埋葬 ruff / pytest / schema check
呢啲作者真係改得到嘅信號。
