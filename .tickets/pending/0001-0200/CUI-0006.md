## 問題描述

`src/common/time.py` 嘅 `parse_datetime(rec_time, timezone="Asia/Hong_Kong")` docstring 寫明：

> Returns: A timezone-aware ``datetime`` in ``timezone``.

但 ISO-with-offset 分支（`elif "+" in rec_time:`）直接 `return dateutil.parser.parse(rec_time)`，
**冇 `.astimezone(tz)`**，所以個 `timezone` 參數對呢條路徑完全無效 —— 永遠攞返**輸入字串自己**嘅 offset。

## 重現步驟

```python
from run365days.common.time import parse_datetime

# ISO with offset — timezone 參數被無視
for tz in ["Asia/Hong_Kong", "America/New_York", "UTC"]:
    print(tz, parse_datetime("2021-10-17T06:10:56+08:00", tz))

# 對照組：naive 輸入正常跟參數
for tz in ["Asia/Hong_Kong", "America/New_York", "UTC"]:
    print(tz, parse_datetime("2021-10-17 06:10:56", tz))
```

## 實際結果

```
ISO-with-offset（全部一樣，參數無效）
  Asia/Hong_Kong     -> 2021-10-17 06:10:56+08:00
  America/New_York   -> 2021-10-17 06:10:56+08:00
  UTC                -> 2021-10-17 06:10:56+08:00

naive（正常跟參數）
  Asia/Hong_Kong     -> 2021-10-17 06:10:56+08:00
  America/New_York   -> 2021-10-17 06:10:56-04:00
  UTC                -> 2021-10-17 06:10:56+00:00
```

四條 input path 之中，只有 ISO-with-offset 呢條唔遵守 `timezone` 參數。

## 預期結果

跟 docstring：回傳值應該轉換到 `timezone`，即
`dateutil.parser.parse(rec_time).astimezone(tz)`。
（注意：呢個係**轉換**，唔會改變絕對時刻，只改變表示嘅 offset。）

## 影響範圍

**目前生產零影響**：全部 caller 都用預設 `timezone="Asia/Hong_Kong"`，而所有真實 Garmin
ISO-with-offset 時間戳本身就係 `+08:00`，所以「輸入 offset」啱啱等於「要求 offset」，
撞啱同結果。現有測試 fixture 全部係 `+08:00`，所以測試亦係撞啱綠。

風險喺於：任何人第一次傳一個非 HK 嘅 `timezone` 落去，會靜靜咁攞到錯嘅 offset，
而且冇任何測試會 fail。

## 與其他 ticket 嘅關係

- **AU-003**（已完成）修嘅係 `.replace(tzinfo=)` 嘅 LMT 問題，唔涉及呢條分支
- **AU-048**（pending）修嘅係 Unix-ms 分支早 8 小時，亦唔涉及呢條分支
- 三者同屬 `parse_datetime` 嘅 input path 一致性問題，**建議一併處理**

## 建議修復方向

`elif "+" in rec_time:` 分支加 `.astimezone(tz)`，並補測試斷言三個唔同 `timezone`
參數下嘅 offset 各自正確。做嗰陣順帶檢查 `"-"` offset（例如 `-05:00`）有冇被
`"+" in rec_time` 呢個條件漏咗 —— 睇落係漏咗，會跌落最後嗰句 `strptime` 而 raise。

## 驗證方式

- 上述重現 script 三個 timezone 各自回唔同 offset 而絕對時刻相同
- 188 條現有測試仍然全綠
