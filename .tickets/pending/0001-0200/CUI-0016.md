## 問題描述

`src/common/time.py` 嘅 `parse_datetime()` 有五種 input 形態，但 **ISO UTC 冇毫秒**嗰種會 raise：

```
2021-10-17T06:10:56Z   →  ValueError
```

原因：第一個分支條件係 `"." in rec_time and rec_time.endswith("Z")` —— 冇毫秒就冇 `.`，條件唔成立。
跟住個字串亦冇 `+`/`-` offset，所以最後跌落 naive `strptime`，格式對唔上就 raise。

## 同 CUI-0006 嘅關係

**同一類缺口，但係唔同條件。** CUI-0006 修好嘅係「有 offset 但係負數」（`"+" in rec_time` 漏咗 `-05:00`），
呢條係「係 UTC 但冇毫秒」。兩者都係**分支條件寫得太窄**，用咗一個表面特徵（有冇 `.`、有冇 `+`）
去代替真正嘅判別。

## 可達性

**目前唔可達** —— 現行 raw corpus 冇任何呢種字串（developer 掃過全部 1095 個 `.tcx` / `.gpx` / `.kml`）。

但 `…Z` 冇毫秒係**完全合法而且好常見**嘅 ISO 8601 形態，任何新資料來源或 Garmin 改格式就會撞到。

## 建議修復方向

唔好再加多一個 `elif`。五種形態（UTC 有毫秒、UTC 冇毫秒、有正 offset、有負 offset、naive）
而家用四個特徵判別條件去分，已經證明咗會漏。

建議改為：**先嘗試 `dateutil.parser.isoparse()`（或 `datetime.fromisoformat()`，Python 3.11+ 支援 `Z`），
成功就按有冇 tzinfo 決定 `astimezone(tz)` 定當 naive 處理；失敗先落 fallback 分支處理
epoch-ms 同其他非 ISO 格式。** 咁樣 ISO 嘅變體由 library 負責認，我哋唔使逐個特徵猜。

⚠️ 改嗰陣必須保住 AU-003 / AU-048 / CUI-0006 三條已修好嘅性質：
- 四條絕對時刻 path 喺任何 `timezone` 參數下都要落喺同一個 UTC 瞬間
- naive path 維持 zone-relative
- epoch-ms 係**轉換**唔係貼標籤

## 驗證方式

- 五種形態 × 三個 timezone 參數，全部正確
- 294 條現有測試全綠
- static JSON 仍然 byte-identical（6,857,102 bytes / 370 files）
