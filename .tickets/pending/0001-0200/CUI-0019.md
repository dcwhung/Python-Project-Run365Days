## 問題描述

`src/api/service._sample_filter()` 為 batch 入面每條 track 砌一條 OR arm：

    or_(and_(activity_id == X1, position.in_([...])),
        and_(activity_id == X2, position.in_([...])), ...,
        activity_id.in_(whole))

SQLite 要對 `row_number() OVER (PARTITION BY activity_id ORDER BY seq)` subquery
嘅**每一 row** 評估呢 N 條 arm（EXPLAIN 顯示 `SCAN (subquery-3)` → `SCAN anon_1`），
所以總成本 ∝ batch 闊度 × batch 總 row 數 = **O(N²)**。
AU-050 之前每條 track 各自一句 index-bounded statement，成本係線性。

## 實測（真實 export，134,041 track rows；`points=1`，service 層，median of 3）

| tracks | 掃過 rows | PRE ms | POST ms | 倍數 | POST ms/1000 rows |
|---|---|---|---|---|---|
| 16 | 5,268 | 18.2 | 16.2 | 0.89x | 3.07 |
| 32 | 11,381 | 35.2 | 51.5 | 1.46x | 4.52 |
| 64（現時 cap） | 23,549 | 67.0 | 158.7 | 2.37x | 6.74 |
| 128 | 47,809 | 141.7 | 553.9 | 3.9x | 11.58 |
| 256 | 94,996 | 281.9 | 1,948.2 | 6.9x | 20.51 |
| 365 | 134,041 | 433.8 | 3,842.3 | 8.9x | 28.67 |

PRE 嘅 ms/1000 rows 平喺 ~3.0（線性）；POST 由 8.5 升到 28.7（平方）。

端到端 HTTP（pre vs post，同一 DB，median of 5）：

| Document | PRE | POST | Delta |
|---|---|---|---|
| `activities(limit:32){track(points:1)}` | 60.5 ms | 57.9 ms | -4% |
| `activities(limit:64){track(points:1)}` | 93.3 ms | 182.5 ms | **+96%** |
| `activities(limit:64){track(points:150)}` | 290.0 ms | 372.8 ms | +29% |
| `activities(limit:64){track(points:156)}` | 300.0 ms | 390.2 ms | +30% |
| `activities(limit:16){track(points:600)}` | 109.0 ms | 149.9 ms | +38% |

Statement count 確實由 130 → 4，但 wall clock 升咗。

## 影響範圍

- **正確性零影響**：4,745 條 batch-vs-single 比對、6,205 次 service 層 pre/post 比對，0 差異。
- **今日冇用戶受影響**：`frontend/src/data/api/queries.ts` 冇任何 document 用
  `activities { track }`；前端 `Track` document 13.8 ms vs baseline 13.2 ms。
- **最差合法 shape 390 ms**，仍然約 38x 喺 Vercel 15 s 之內。
- **真正風險喺前面**：`MAX_TRACK_FIELDS_PER_REQUEST` 嘅 docstring 明文話 AU-050
  "weakens the round-trip argument for keeping this number where it is"。
  調高 cap 正正係呢個實作最差嘅方向（128 → 3.9x，365 → 8.9x / 3.8 秒）。

## 建議修復方向（由 developer 判斷）

1. 用 `VALUES` / CTE 代替 N 條 OR arm：把 `(activity_id, position)` 對砌成一個 CTE，
   同 numbered subquery inner join，令 predicate 變成可用 index / hash 嘅 join。
2. 或者只 batch **COUNT**（`_stored_counts` 本身已經係一句 grouped COUNT，冇問題），
   SELECT 保留 per-track —— statement 由 2N 變 N+1，而且唔會引入平方項。
3. 無論邊條路，都要加一個**隨 batch 闊度檢查成本線性**嘅 test
   （例如比 `tracks(ids[:16])` 同 `tracks(ids[:64])` 嘅 rows-examined 比值，
   而唔係 wall clock——wall clock 喺 CI 只會買到 flaky test）。
4. 量度基準要用 production 規模（見 CUI-0020）；600-row fixture 睇唔到呢個問題。
