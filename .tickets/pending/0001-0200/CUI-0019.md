# CUI-0019 `num_points` 係降採樣前嘅點數，但讀落似「可取得嘅點數」

**狀態**：pending
**類型**：bug
**優先級**：🟡 Medium
**來源**：AU-047 評估過程中由 Main agent 實測發現
**建立日期**：2026-09-14

---

## 問題描述

`src/export/records.py:120` 寫 `"num_points": len(points)` —— 呢個係**降採樣之前**嘅原始解析點數。
但實際存入 `track_points` table 嘅行數受 `run365-export --points`（預設 600）封頂。

兩者對絕大部分 activity 相同，**因為大部分跑步嘅原始點數本來就少過 600**。

## 實測（365 條真實 activity）

```
365 條入面 num_points != 實際 track row 數 嘅有: 2 條

id            num_points  stored  has_gps  distance_km
6701104700           653     600        1  10.14
7264441638          1250     600        1  11.22

全庫最大 num_points = 1250 ｜最大 stored = 600
```

## 影響

### 1. 語義誤導，而且已經到咗 client

`numPoints` 喺 GraphQL schema 有暴露（`src/api/schema.py:178`、`frontend/schema.graphql:17`），
而前端 `ActivityFields` fragment **每個 activity query 都攞緊佢**。

即係 API 話呢條 activity 有 1250 點，但 `track` field 最多只俾到 600 —— 兩個數字互相矛盾，
而冇任何嘢講明點解。

### 2. 令一個睇落安全嘅優化變成陷阱

AU-047 有個「平手位」構想：`_even_sample_filter`（`src/api/service.py:167`）每次都跑一個
`SELECT COUNT(*)`，而 `models.Activity.num_points` 表面上已經存住同一個數，可以直接讀返、
慳走一個 query。

**但因為 `num_points` 係降採樣前嘅數，呢個代換會喺嗰兩條 activity 上面計錯 stride** ——
以 1250 為總數去算位置，但實際只有 600 行。**而且錯嘅正正係點數最多、最需要降採樣嗰兩條。**

Main agent 曾經兩次向用戶建議呢個做法，實測之後推翻。

## 建議修復方向

呢個係**語義決定**，唔應該由 developer 單獨拍板：

**方案 A —— `num_points` 改為「已儲存點數」**
- `records.py:120` 改為降採樣後嘅長度
- 優點：欄位名同內容一致；AU-047 嗰個優化即刻變安全
- 缺點：`data/processed/*.db` 要重新 export（唔影響 `data/raw/`）；**會改變 static JSON 輸出** → 打破 byte-identical 基準（呢個係本 session 每輪都守住嘅網，要明確接受）

**方案 B —— 保留語義，改名兼補一個新欄位**
- `num_points` → `num_source_points`（原始解析點數），另加 `num_stored_points`
- 優點：兩個數字都有，語義清晰
- 缺點：GraphQL schema 改動（`num_points` 移除係 breaking change，前端要改）

**方案 C —— 只補文件**
- 喺 dataclass / SDL description 寫明「解析所得嘅原始點數，可能多過 `track` 實際回傳嘅點數」
- 優點：零行為改動、零回歸風險
- 缺點：矛盾仍然存在，只係寫低咗

⚠️ 無論邊個方案，**AU-047 唔可以用 `num_points` 代替 COUNT**，直到呢張票解決為止。

## 驗證方式

- 365 條 activity 全部 `num_points` 同實際 row 數關係符合所選方案
- 若選 A：明確記錄 byte-identical 基準已更新，並記低新基準
- 現有測試全綠
