# CUI-0052 兩個 supply-chain audit gate 坐喺 deploy 上游，一條無關 advisory 可以停晒部署

**狀態**：✅ done（2026-09-17）—— 跟方案 B ＋ C 嘅交集，見最後一節
**類型**：ci / supply-chain
**優先級**：🟢 Low
**來源**：Code Review 2026-09-17（S-122）
**建立日期**：2026-09-17
**建立人**：Backend Developer（cleanup lane，由 Code Reviewer 發現）
**負責人**：DevOps Engineer
**相關**：CUI-0036（npm audit 入 CI）、CUI-0044（pip-audit 入 CI）、S-122、W-034 / S-095（allowlist 漂移嘅先例）

---

## 問題描述

`.github/workflows/pages.yml` 嘅 job 圖（實測核實）：

```
lint-test  ──┐                （最後一步：pip-audit）
             ├──> build ──> deploy
frontend   ──┘                （最後一步：npm audit）

build.needs  = [lint-test, frontend]
deploy.needs = build
build.if / deploy.if = github.ref == 'refs/heads/develop'
```

兩個 audit gate 都係 **hard gate**，而且**預期**會因為「上游啱啱出咗個 advisory」而紅 ——
呢點 `pages.yml` 自己明文寫住，係刻意嘅設計。

同時，本 repo **每次 push `develop` 就 deploy**（GitHub Pages + Vercel production branch 都係 `develop`）。

兩件事合埋：**一條同本 repo 完全無關嘅上游 advisory，可以令所有部署停晒，包括一個 hotfix。**

實測佐證（2026-09-17，本 worktree 嘅 `.venv`）：喺未 upgrade `pip` / `setuptools` 之前，
`pip-audit` 報 **14 條**（pip 24.0 ×12、setuptools 79.0.1 ×2），全部同本 repo 十個 runtime dependency 無關。
呢批係靠 step 自己第一行 upgrade 洗走嘅；但 upgrade 掂唔到嘅第三方 advisory 就冇呢條退路。

## 影響

🟢 Low，**唔係缺陷**。呢個 trade `pages.yml` 同 `docs/deployment.md` 都認咗係刻意嘅。
開票唔係要推翻佢，係要問一句**之前冇問過**嘅嘢：呢個 trade 喺「要出 hotfix 嗰日」係咪仲成立。

反面理由同樣企得住：hard gate 嘅價值正正在於冇得繞。一個「趕住出嘢就跳過 supply-chain 檢查」嘅制度，
喺最需要佢嘅時候（趕住補洞）就冇咗。呢個係一個**取捨**，唔係一個 bug。

## 建議

**方案 A**：維持現狀，唔郁 workflow。已經喺 `docs/deployment.md` 明文寫低咗呢個 trade（S-122 (a) 已落）。
　*優點*：零改動；hard gate 冇得繞呢點保住。
　*缺點*：hotfix 嗰日先發現，就已經太遲。

**方案 B（標準做法）**：把兩個 audit 由部署路徑**解耦** —— 另開一個 `schedule:`（例如每日）嘅
獨立 audit workflow，紅咗開 issue / 通知，但唔 block `build` → `deploy`。
　*優點*：供應鏈漂移唔再坐喺部署路徑上；仍然日日審，唔會冇人睇。
　*缺點*：一個帶住已知 advisory 嘅 PR 可以 merge 埋去；要靠人睇 issue。

**方案 C**：保留喺 PR 上 block，但喺 `develop` push（即係 deploy 嗰條路）上唔 block。
　*優點*：PR 審查照舊嚴；hotfix 出得去。
　*缺點*：兩套 threshold，`pages.yml` 會更複雜；而且 deploy 先係最要緊守嗰關。

⚠️ **`continue-on-error` 唔係答案**：佢等於把 gate 留喺版面上但拎走佢唯一嘅作用，
之後個 workflow 睇落有 SCA 其實冇。同一個道理令 `--ignore-vuln` allowlist 喺 CUI-0044 被否決
（W-034 / S-095 兩個先例：exception list 會漂移，之後個 gate 報緊嗰張 list 而唔係報緊棵樹）。

## 驗證方式

- 揀咗方案之後：確認 `build.needs` / `deploy.needs` 同新設計一致
- 如果揀 B：確認 scheduled workflow 真係會紅（用一個 upgrade 掂唔到嘅第三方 package 做紅種，
  例如 `pip install jinja2==3.1.2` —— CUI-0044 已經用呢個方法驗過 gate 嘅偵測力）
- 如果揀 B 或 C：確認 `docs/deployment.md` 同 `CLAUDE.md` §3 兩處描述同步更新

## 2026-09-17 —— 落地決定：**方案 B ∩ C**，兩個 audit 搬去 `.github/workflows/audit.yml`

### 做咗啲乜

兩個 audit step **原封不動**搬去一個新 workflow `audit.yml`（`push` / `pull_request` 去
`develop` + `master`、每日 `schedule:`、`workflow_dispatch`）。`pages.yml` 淨低
lint / test / typecheck / build → `build` → `deploy`。**冇任何 job `needs` 個 audit**。

指令、threshold、branch list 全部一模一樣；改嘅只係 **dependency edge** 一樣嘢。
理由書（`pip` / `setuptools` upgrade 點解係 fix 唔係 suppression、`npm audit` 點解審全樹）
逐字跟住 step 搬過去，冇留喺 `pages.yml` 做孤兒。

### 點解唔係方案 A（維持現狀）

方案 A 企得住嘅理由係「hard gate 嘅價值在於冇得繞」。但實測之下呢個理由**喺呢個 repo 本身就唔成立**：

```
GET /repos/dcwhung/Python-Project-Run365Days/branches/develop  →  "protected": false
GET /repos/dcwhung/Python-Project-Run365Days/branches/master   →  "protected": false
```

`develop` / `master` 兩邊都**冇 branch protection、冇 required status check**（2026-09-17 量）。
所以兩個 audit 由頭到尾都**唔係**一個「冇得繞」嘅 gate ——
佢哋唯一嘅強制力係「有人見到紅」，而搬完之後呢一點**一個字都冇變**。

真正被佢哋擋住嘅只有一樣嘢：**部署**。而部署正正係最唔應該被一條上游 advisory 擋住嗰樣。

### 點解唔係 `if: github.event_name == 'pull_request'`（票入面嘅方案 C 原形）

方案 C 寫住「PR 上 block，`develop` push 上唔 block」。實測之下呢個做法有個**真窿**：
本 repo **有**唔經 PR 直接 push 去 `develop` 嘅路徑，而且正正就係 hotfix 嗰條路。
`develop` first-parent 歷史入面，`fd252a3` → `c3a23e0` → `abdb6ad` → `e506531` →
`12c31fe` → `5aa1b2f` → `2f1a1da` 加埋 `65e2d27`，呢一段就**八個單 parent commit 直接落 `develop`**（再上去仲有，`93d2dcb`、`6468267` …），
全部係當年追 Vercel 部署嗰場仗。呢啲 commit 喺方案 C 之下會**完全冇審過**。

搬 job 冇呢個問題：`push` 同 `pull_request` 兩個 trigger 都跑同一個 job，
直接 push 一樣審，紅一樣紅。

### 點解唔係 `continue-on-error`（票入面已經否決，實測後同意）

同意票上講法，冇新嘢加。`continue-on-error: ${{ github.event_name != 'pull_request' }}`
呢個變體亦一樣否決：佢係同一件事戴頂帽，而且仲差 —— 個 step 喺 push 上會顯示成
「✅ 過咗」而唔係「跳過咗」，讀 workflow 個人分唔出。

### 加咗每日 `schedule:`（方案 B 嗰半）

push-triggered audit 只量到「有人 push 嗰一刻」棵樹，而上游漂移行佢自己嘅鐘。

⚠️ **兩個 GitHub 規則喺呢個 repo 特別咬人，兩個都係靜英英，所以明文寫低**：

1. `schedule` **只會用 default branch 上面嗰份 workflow file**。本 repo default branch 係
   `master`，唔係 deploy 源頭 `develop`。⇒ **`audit.yml` merge 落 `develop` 之後，每日嗰 run
   一次都唔會行**，要等下次 release merge 上 `master` 先生效。`push` / `pull_request`
   冇呢個限制，落咗 `develop` 即刻生效 —— 所以**取代舊耦合嗰樣係 push/PR，唔係個 schedule**。
2. scheduled run 預設 checkout default branch（`master`，release 之間落後 `develop`）。
   兩個 job 個 `actions/checkout` 都明文寫咗 `ref: develop` 俾 schedule 用。

### 冇做嘅嘢

**冇自動開 issue**。日日開一張同一條 advisory 嘅 issue 就係噪音，加 dedup 就要維護一張
「開咗未」嘅狀態 —— 同 W-034 / S-095 嗰種「維護一張會漂移嘅 list」係同一個形狀。
紅嘅信號係：commit / PR 上面嗰個紅 check（同搬之前一模一樣），加 Actions tab，
加 GitHub 對 scheduled workflow 失敗發俾「最後改過 cron 嗰個人」嘅通知。

### 部署鐵律核對（parsed YAML，唔係讀原文）

```
build.needs  = ['lint-test', 'frontend']          （不變）
deploy.needs = 'build'                            （不變）
build.if = deploy.if = "github.ref == 'refs/heads/develop'"   （不變）
pages.yml concurrency group / cancel-in-progress               （不變）
audit.yml: 兩個 job 都 needs=None、if=None        （即係話冇嘢掛喺佢哋後面）
```
