## 問題描述

`src/api/app.py:22-25` 每個 request 開一個 session，靠 `response.call_on_close(session.close)` 收工：

```python
def get_context(self, request, response):
    session = db.Session(self._engine)
    response.call_on_close(session.close)
    return {"request": request, "response": response, "session": session}
```

`call_on_close` 要 WSGI iterable 真係被 close 先會行。真 WSGI server 會，
Flask 嘅 `app.test_client()` 唔會。所以喺測試入面 session 一路積落去，
去到 SQLAlchemy 預設 `QueuePool`（size 5 + overflow 10 = 15）滿咗，
第 ~134 個 request 就開始 30 秒 timeout。

**呢個唔係 production bug** —— 已經用真 WSGI server 排除咗（見下）。
但佢係一個會令人查錯方向嘅測試陷阱，而 AU-001 啱啱加咗 paging，
正正令「喺一條測試入面 loop 幾百個 request」變成一個好自然會出現嘅 pattern。

## 重現步驟

```python
app = create_app(db_path, graphiql=False)
c = app.test_client()
for i in range(400):
    c.post("/api/graphql", json={"query": "query($o:Int!){activities(limit:1,offset:$o){id}}",
                                 "variables": {"o": i}})
```

## 預期結果

測試 client 同真 server 有相同嘅 session 生命週期，測試唔會因為 request 數量而失敗。

## 實際結果

```
### S20b  400 sequential requests
  real WSGI server:    400 ok, 0 failed; walked 365 ids, unique=365
  Flask test client:   request 134 -> QueuePool limit of size 5 overflow 10 reached,

```

真 server 400/400 全過，分頁行走結果同一次過攞完全一致（365 unique ids）。
只有 test client 會爆。

## 建議修復方向

擇一：

1. 喺 `tests/` 加一個 fixture，request 之後主動 `response.close()`（最細改動，唔郁 production code）
2. `src/api/db.py` 嘅 `make_engine` 用 `poolclass=NullPool` —— 對一個 read-only
   SQLite file 嚟講 connection pooling 本身收益好細，而且 serverless 環境下反而更乾淨
3. `_SessionView` 改用 Flask `teardown_request` 而唔係 `call_on_close`，
   咁真 server 同 test client 兩邊行為一致

建議 (2) 或 (3)，因為 (1) 只係喺測試側遮住，個不一致仍然喺度。

## 驗證方式

- 一條新測試 loop 400 個 request 都唔會 timeout
- 真 WSGI server 仍然 400/400（唔可以為咗修測試而整壞 production 路徑）
- 185 條現有測試全綠
