## 問題描述

`src/common/geo.py:31` 收到非有限座標時，numpy 只會發
`RuntimeWarning: invalid value encountered in sin/cos`，然後回一個 `nan`，
唔會拒絕輸入。

## 可達性

**經 GPX / KML 已唔可達** —— CUI-0001 已將兩者嘅 lat / lon 讀取硬化成
`parse_finite_float()`。但 `haversine_distance` 係 public function，
in-process caller 仍然可以直接餵 inf / nan 落去。

CUI-0001 修復前實測：`lat_inf_2102.gpx` 令 `distance_by_coord_km = 0.0` —— **靜默**，
就係經呢條 sin/cos 路徑。

## 建議修復方向

於 `haversine_distance` 入口加有限性檢查，非有限即掟明確錯誤而唔係回 `nan`。
留意佢係 hot path（`total_track_distance` 逐點呼叫），檢查要用向量化做法，
唔好逐點 Python-level 檢查 —— 順帶參考 AU-039（該函數而家用 `DataFrame.apply()`
逐點算，本身已經係最慢寫法）。

## 驗證方式

- 直接餵 `inf` / `nan` 座標，得到明確錯誤而非 `nan`
- 365 個真實檔案 export 後 static JSON 仍然 byte-identical
- 209 條現有測試全綠

## 修復（2026-09-17，base HEAD `6576e56`）

`src/common/geo.py` —— `haversine_distance()` 喺解包 `None` 檢查之後、交俾 numpy 之前，
加一個四項短路 `math.isfinite` guard，任何 `±inf` / `nan` component 即掟 `ValueError`。
`None` 嘅舊行為（回 `np.nan`，indoor run 段數照樣跌出 sum）**完全不變**。

### 掟 `ValueError` 而唔係新 exception type 嘅理由

`BaseActivityParser.parse_all` 已經有 `except ValueError` 分支（`base.py:207`），
會將出事嘅檔案連檔名喺 WARNING log 出嚟然後跳過 —— 即係同 `ActivityParseError` 一樣嘅
per-file containment，唔會拖冧成個 export。掟 `ActivityParseError` 讀落好啲，但
`common/` import `activities/` 會倒轉分層（`activities` 單向 import `common`）。

### 實測推翻票上兩處講法

**1. 票寫「只出 `RuntimeWarning`」—— 只啱一半。**
實測（base HEAD `6576e56`）：`±inf` 的確出兩個 `RuntimeWarning: invalid value
encountered in sin/cos`；但 `nan` 座標**連一個 warning 都冇**，`np.sin(nan)` / `np.cos(nan)`
唔會 set invalid flag。即係 `nan` 路徑比票描述嘅更靜。兩者都回 `nan`：

```
haversine_distance((inf, 114.2), (22.3, 114.2))  -> nan  + 2 RuntimeWarning
haversine_distance((nan, 114.2), (22.3, 114.2))  -> nan  + 0 warning
total_track_distance([(22.28,114.1588), (nan,114.16), (22.3193,114.1694)])
                                                 -> (0.0, 2)   # 靜默零
```

**2. 票寫「檢查要向量化，唔好逐點 Python-level 檢查」—— 前提唔成立。**
逐點 `math.isfinite` guard 喺呢個 scale 量唔到。

| 量度 | 方法 | 結果 |
|---|---|---|
| A/B on `total_track_distance`，N=3600 | 交錯 noguard/guard，各一個 fresh process，5 對，取 median | noguard 35.01 ms／guard 34.91 ms（−0.3%） |
| A/B on `total_track_distance`，N=10000 | 同上 | noguard 96.05 ms／guard 96.33 ms（+0.3%） |
| guard 表達式本身 | `timeit`，min of 7 × 200k | **0.060 µs** ／call |
| `haversine_distance` 全個 call | `timeit`，min of 7 × 20k | **3.56 µs** ／call |
| `total_track_distance` 每段端到端 | 96 ms ÷ 9999 段 | **≈9.6 µs** ／段 |

兩次 A/B 差異方向相反、而且都細過單一 arm 自己嘅 spread（±6%）—— 即係 guard 喺噪音之下。
唔受噪音限制嘅 `timeit` 給出上界：guard = 一個 `haversine_distance` 嘅 **1.7%**，
= 一段端到端成本嘅 **0.6%**。真正食掉 ~63% per-segment 成本嘅係 `DataFrame.apply`
嘅逐行 dispatch —— 即 **AU-039**，唔喺本 lane，本次改動冇令佢更慢（距離讀數
`13.245655394` 改前改後 byte-identical）。

### Mutation proof

唔改源碼，用 pytest plugin 喺 `pytest_configure` 做 in-process `setattr`，
每個 mutant 先用一個獨立 oracle **assert 佢真係生效咗**先至行測試（`__pycache__` 已清）：

| Mutant | oracle 確認生效 | 結果 |
|---|---|---|
| 刪走 guard（還原 pre-fix body） | inf 回 `nan` 而唔 raise ✅ | **殺死**，13 failed |
| guard 只檢查 origin，唔檢查 destination | origin-inf raise、destination-inf 回 nan ✅ | **殺死**，5 failed |
| guard 連 `None` 都拒絕 | `(None, 114.0)` raise ✅ | **殺死**，3 failed |

`test_guard_fires_before_numpy_sees_the_value` 係專門答「一條只 assert 會 raise
嘅測試，點證明佢真係紅」嘅：佢用 `warnings.simplefilter("error")` 包住，
guard 一被刪，inf 個 case 就以 **`RuntimeWarning`**（而唔係 `ValueError`）現形，
nan 個 case 就係 DID NOT RAISE —— 兩個方向都紅，而且紅嘅原因唔同，分得開。
