# CUI-0042 `tag-release.yml` 冇辦法更正一份已發佈嘅 Release notes —— tag 已存在就直接 exit 1

**狀態**：✅ done
**類型**：ci / process gap
**優先級**：🟢 Low
**來源**：v3.2.0 release 過程（2026-09-16）實際撞到
**建立日期**：2026-09-16
**建立人**：Main Agent
**負責人**：DevOps Engineer
**相關**：`.github/workflows/tag-release.yml`、S-079（CHANGELOG 係 release notes 嘅來源）

---

## 問題描述

`tag-release.yml` 係一條**單向**流程：建 tag，再由 `docs/CHANGELOG.md` 抽對應 section
做 GitHub Release notes。一旦 tag 建咗，成條 workflow 就再冇路可以行：

`.github/workflows/tag-release.yml`

```yaml
- name: Validate tag name
  run: |
    [[ "$TAG" =~ ^v[0-9]+\.[0-9]+\.[0-9]+$ ]] || { echo "Tag must look like v1.2.3, got '$TAG'"; exit 1; }
    if git ls-remote --tags origin "refs/tags/$TAG" | grep -q .; then
      echo "Tag $TAG already exists on origin"; exit 1        # ← 呢度封死
    fi
...
- name: Create GitHub Release
  if: inputs.release
  run: gh release create "$TAG" --title "$TAG" --notes-file release-notes.md --verify-tag
```

即係話：**CHANGELOG 喺 tag 之後有任何更正，都同步唔返落已發佈嘅 Release body。**

## 實際撞到（v3.2.0，2026-09-16）

v3.2.0 個 CHANGELOG entry 入面有一句數字自相矛盾 —— 開頭段寫
「Twelve tickets and **twenty-seven** review items」，下面 `Documented` 一條卻寫
「**Twenty-two** review items」（舊草稿殘留）。發現嗰陣 tag 已經建咗、Release 已經發佈。

- Repo 側修得返：PR #16 → `5f55e36`，`docs/CHANGELOG.md` 而家兩處一致
- Release body 側修唔返：重跑 `tag-release.yml` 會喺 `Validate tag name` 直接 `exit 1`；
  workflow 亦冇 `gh release edit` 路徑
- **最後由人手喺 GitHub Release UI 改一隻字**

一個一隻字嘅更正要離開自動化、用 UI 補飛 —— 呢個就係要修嘅嘢。

## 影響

低。但呢條路**每次 release 都會走**，而「CHANGELOG 喺 tag 之後先發現要更正」唔係罕見情況
（本 repo 呢個 session 就中咗一次）。人手改 Release UI 有兩個問題：

1. 冇 audit trail —— 邊個改咗乜、幾時改，唔喺 repo 入面
2. Release body 同 `docs/CHANGELOG.md` 會靜靜地分歧，而兩者本來應該係同一份嘢

## 建議

加一條 **idempotent 路徑**：tag 已存在時唔好 `exit 1`，改為只重新抽 notes 再
`gh release edit`。

**方案 A（推薦）** —— 加一個 `notes_only` boolean input：

- `notes_only: false`（預設）＝ 今日行為，tag 存在就 `exit 1`（**保住呢個保護**，
  因為佢擋住「唔覺意 re-tag 一個已發佈版本」）
- `notes_only: true` ＝ 跳過建 tag，只行抽 notes + `gh release edit "$TAG" --notes-file release-notes.md`；
  如果 tag **唔**存在就 `exit 1`（反向保護）

Trade-off：多一個 input，但兩個方向嘅保護都齊，而且意圖喺 dispatch 嗰刻就講明。

**方案 B** —— `Create GitHub Release` 一步改成 `gh release create ... || gh release edit ...`。

Trade-off：改動最細，但會令「tag 已存在」由一個**錯誤**變成一個**靜默嘅正常情況**，
削弱咗 `Validate tag name` 嗰個保護。唔建議。

## 驗證方式

- `notes_only: true` 對一個**已存在**嘅 tag 行 → Release body 更新成 CHANGELOG 現時內容，
  tag 本身唔郁（`git rev-list -n1 <tag>` 前後相同）
- `notes_only: true` 對一個**唔存在**嘅 tag 行 → 紅，訊息講明要先建 tag
- `notes_only: false`（預設）對一個**已存在**嘅 tag 行 → 仍然紅（今日行為唔可以變）
- `notes_only: false` 對一個新 tag 行 → 同今日一樣，建 tag + 建 Release
- 用 v3.2.0 做真實 case 驗一次：跑 `notes_only: true`，Release body 應該由人手改過嗰版
  變成由 CHANGELOG 生成嗰版，兩者內容應該一致（即 no-op 但證明條路行得通）

## 執行紀錄

採用**方案 A**。方案 B 冇做（票明確唔建議：會令「tag 已存在」由錯誤變成靜默正常情況）。

`.github/workflows/tag-release.yml` 五處改動：

| 位置 | 改動 |
|---|---|
| header comment | 加一段講兩個 mode、點解存在（v3.2.0）、同埋 `release` 喺 `notes_only` 之下被忽略 |
| `on.workflow_dispatch.inputs` | 加 `notes_only` boolean，`default: false` |
| `Validate tag name` | 分兩路：`notes_only=false` 要求 tag **唔存在**（今日行為）；`notes_only=true` 要求 tag **存在**。tag 名 regex 兩路照行。紅嗰陣多一句指返路（「re-run with notes_only: true」）|
| `Create and push annotated tag` | 加 `if: ${{ !inputs.notes_only }}` |
| `Extract release notes…` | `if:` 由 `inputs.release` 放寬到 `${{ inputs.release \|\| inputs.notes_only }}` |
| `Create GitHub Release` | `if:` 收窄到 `${{ inputs.release && !inputs.notes_only }}` |
| **新** `Update the published Release notes` | `if: ${{ inputs.notes_only }}` → `gh release edit "$TAG" --notes-file release-notes.md` |

`gh release edit` 特意係**獨立一個 step**，唔係 `create \|\| edit` fallback —— 理由寫咗喺
step 隔籬嘅 comment。

### 驗證方式：全部靜態。**冇 dispatch 過呢個（或者任何）workflow。**

票上四個 case 都要喺冇 runner / 冇網絡 / 冇 `gh` 之下追一次，所以分三層：

1. **`actionlint` 1.7.7**（下載落 scratchpad，唔入 repo）行 `tag-release.yml` 同 `pages.yml`
   → **exit 0**。⚠️ 呢部機**冇 `shellcheck`**，所以 actionlint 嘅 shellcheck integration
   冇行過，佢驗到嘅係 YAML schema、expression 語法同 `inputs.*` context，唔係 shell 本身。
2. **Step gating**：用 PyYAML 解析個 workflow，逐個 step 計佢個 `if:`（只需要支援
   `inputs.x`、`!`、`&&`、`||` 呢幾種，workflow 入面得呢啲）。
3. **Shell**：`Validate tag name` 個 `run:` body **原文**攞出嚟，用 `bash -e -c`
   （同 GitHub 預設 `bash -e {0}` 一樣）真係行一次，`PATH` 前面放一個假 `git`
   stub 扮 `ls-remote` 有／冇命中。即係話下面 `exit 1` 同 stdout 都係**真行出嚟**嘅。

### 四個 case 嘅 control flow（實際輸出）

| Case | `notes_only` | tag 喺 origin | 行到嘅 step |
|---|---|---|---|
| **A** 今日 happy path | false | 唔存在 | checkout → Validate（pass）→ **Create and push annotated tag** → Extract notes → **Create GitHub Release** → *skip* Update notes |
| **B** 今日嘅保護 | false | 存在 | checkout → Validate **exit 1**（`Tag v3.2.0 already exists on origin` ＋ 指去 `notes_only: true`）→ 之後全部唔行 |
| **C** CUI-0042 嘅修復 | true | 存在 | checkout → Validate（pass，印 `the tag will not be touched`）→ *skip* Create tag → Extract notes → *skip* Create Release → **Update the published Release notes** |
| **D** 反向保護 | true | 唔存在 | checkout → Validate **exit 1**（`notes_only asked to correct v3.2.0, but no such tag exists on origin`）→ 之後全部唔行 |

A / B 同改動前逐步一致（B 只多咗一句指路），C 係新路，D 係新保護 —— 即票上四條驗證方式
全部對得上，除咗最後嗰條「用 v3.2.0 真跑一次」：嗰條要 dispatch，**留返俾有權限嗰位行**。
行嗰陣預期 C 係 no-op（Release body 而家已經係人手改到同 CHANGELOG 一致），
但會證明條路真係通。
