## 問題描述

`src/api/service.py` 嘅 `SAMPLE_KEY_SEPARATOR` docstring（W-026 改寫之後）明文寫低
**key 唯一承重嘅性質**：

> What makes the key injective is that one of its two halves cannot contain this
> character … Let that change and both orders break together, and the key stops
> matching silently rather than raising.

呢句係啱嘅（QA 已用反例證實，見下）。問題係：**冇任何一條測試會因為佢被違反而紅。**

QA 用 in-process mutation（唔改 repo 任何檔案）將 `SAMPLE_KEY_SEPARATOR`
由 `":"` 改成 `"0"`（十進制數字，直接違反 docstring 講嘅性質），再改成 `""`（完全冇分隔符）：

| Mutation | 全套測試 |
|---|---|
| `SAMPLE_KEY_SEPARATOR = "0"` | **365 passed** ❌ 冇一條紅 |
| `SAMPLE_KEY_SEPARATOR = ""` | **365 passed** ❌ 冇一條紅 |

作為對照，同一批 mutation 之中，其餘**有**被守住嘅 invariant 全部即刻紅：

| Mutation | 全套測試 |
|---|---|
| `_even_positions()` 回 `float` | ✅ 紅（`test_activity_with_nested_weather_and_track`） |
| `total <= points` 改成 `total < points` | ✅ 紅（`test_a_batch_mixing_sampled_and_whole_tracks_stays_at_two_arms`） |

## 點解而家啲測試捉唔到

`tests/test_api.py` 嘅兩個 fixture 嘅 activity id 分別係 `r0` 同 `v0`..`v8`
（`VARIED_IDS = tuple(f"v{i}" ...)`）—— **全部有一個非數字前綴，而且長度一致**。
有非數字前綴，`"5" + "0" + "v3"` 一樣拆得返，所以個 separator 係咩根本冇所謂。
Production export 嘅 id 全部係 **10 位固定長度**純數字，同樣救返一鑊
（QA 實測：喺真實 export 上用 `"0"` / `""` / `"5"` 做 separator，輸出**同 `":"` 完全一樣**）。

即係話：**冇一個 fixture 有「令 separator 變成承重」嗰種形狀**。

## 個 invariant 係真嘅（反例）

QA 另建一個 export-shaped DB，activity id 用**變長純十進制**
（`"1"`, `"01"`, `"10"`, `"2"`, `"20"`, `"002"`，每條 60 行），`points=7`：

| separator | 結果 |
|---|---|
| `":"` | ✅ 六條 track 全部啱 |
| `"0"` | ❌ activity `"01"` 回 **10 行**（應該 7 行）—— key collision 撈多咗行 |
| `""` | ❌ 同上 |

碰撞來源：`position=5, id="01"` → `"5001"`；`position=50, id="1"` → `"5001"`。
同 docstring 講嘅一模一樣：**靜靜雞 match 錯，唔會報錯**。

## 影響範圍

- **今日零正確性影響**：production id 全部 10 位純數字，固定長度令任何 separator 都 injective；
  QA 喺真實 export 上 4,069,984 次 field 比對、HTTP 層 117 個 shape 全部零差異。
- **風險係將來**：id 形態由 `file_path.stem.rsplit("_", 1)[-1]` 決定
  （`src/activities/parsers/{tcx,gpx,kml}.py`），唔係 schema 強制。
  換 Garmin export 格式 / 加第二個 data source / 手動改名，都可以令 id 變長短唔一。
  加上 separator 本身係一個冇 gate 嘅 module 常數，兩者夾埋就係一個靜默錯數據路徑。
- **同 W-020 / W-025 / W-026 同一個失敗模式**：
  「斷言式判斷同數字一樣要指到一條會紅嘅測試」（`2026-09-15` batch review §508）。
  今次唔係論證錯（W-026 已經改啱咗），係論證**冇 gate**。

### 撤回一句假「實測」

上面「執行備註（Lane E）」第二段聲稱「票上寫嘅反例形狀重現唔到 …… 冇碰撞」。
**呢句係錯嘅。票上嗰組形狀確確實實會撞，QA 由頭到尾都啱。**

重新量度（本 branch，用 repo 自己個 `tests/test_api.py::_write_id_track_db` 砌返票上原形狀，
id `("1","01","10","2","20","002")`、每條 60 行、`points=7`，每個 separator 一個 fresh process，
mutation 用 in-process `setattr` 所以完全唔經 `.pyc`）：

| separator | 每條 track 回幾多行 | 判定 |
|---|---|---|
| `":"` | `{'1': 7, '01': 7, '10': 7, '2': 7, '20': 7, '002': 7}` | ✅ 冇碰撞 |
| `"0"` | `{'1': 7, '01': **10**, '10': 7, '2': 7, '20': 7, '002': 7}` | ❌ 撞 |
| `""` | `{'1': 7, '01': **10**, '10': 7, '2': 7, '20': 7, '002': 7}` | ❌ 撞 |
| `"5"` | `{'1': 7, '01': 7, '10': 7, '2': 7, '20': 7, '002': 7}` | ✅ 冇碰撞 |

### 碰撞嘅確實來源（順帶收緊 QA 嗰句）

`_even_positions(60, 7)` = `[0, 10, 20, 30, 39, 49, 59]`。
QA 上面寫「`position=5, id="01"` → `"5001"`；`position=50, id="1"` → `"5001"`」——
**個結果（10 行）啱，但呢一對唔係實際嗰對**：5 同 50 都唔係 `points=7` 之下嘅 sampled position。
實際係 id `"1"` 嘅三個 sampled position 撈多咗 id `"01"` 三行（separator = `"0"`）：

| wanted key（來自 id `"1"`） | 撈中 id `"01"` 嘅 row |
|---|---|
| `position=10` → `"1001"` | `position=1` → `"1001"` |
| `position=20` → `"2001"` | `position=2` → `"2001"` |
| `position=30` → `"3001"` | `position=3` → `"3001"` |

7 個正當 sample + 3 行多餘 = **10 行**。`""` 之下同樣三對（`"101"` / `"201"` / `"301"`）。
形狀同 `COLLIDING_IDS` docstring 嗰個 worked example（`position=10` on `"5"` 對 `position=1` on `"05"`）
**完全一致** —— 即係話 Lane E 換 fixture 之後砌嘅係同一個機制，只係佢以為自己推翻咗票上嗰個。

### 點解 Lane E 會量錯（兩個候選成因，都重現到，但都證唔到當時就係佢）

1. **`IN` 係「wanted key 對表入面所有 row」，唔係「wanted 對 wanted」。**
   如果淨係將 wanted key 兩兩相比，**四個 separator 全部都報「冇碰撞」**（實測：
   `":"` / `"0"` / `""` / `"5"` 嘅 wanted-vs-wanted clash 一律 `none`）——
   同 Lane E 講嘅「三個 separator 之下輸出完全一樣」一字不差。
   碰撞係出喺 `"1"` 嘅 wanted key 撈中 `"01"` 一行**冇被 sample 嘅** row，兩邊都唔係 wanted。
2. **Stale `.pyc`（已獨立重現）**：`SAMPLE_KEY_SEPARATOR = "0"` 同 `= ":"` **byte size 一樣**，
   秒級 mtime 亦相同，而 CPython 嘅 `.pyc` 失效只睇「秒級 mtime + size」，
   所以同一秒改完即刻 import 會攞返 stale `.pyc`，量緊個**根本冇 mutate 過**嘅常數。
   `""` 少一個 byte，所以會重新 compile，第 2 點解釋唔到 `""` 嗰個結果 ——
   第 1 點三個 case 全部解釋得到。
   ⚠️ **`python -B` 救唔到**：`-B` 只係唔**寫** `.pyc`，照**讀**現有嗰個（實測 A/B/C 三個 case，
   得「清 `__pycache__`」嗰個至真係量到 `'0'`）。

   > **S-068 更正（量度對象）**：本節原文寫「**實測 size 10 vs 10**」同「`""` **size 9**」。
   > 呢三個數係一個**最小重現模組**（得 `SEP = ':'` 一行）嘅 byte size，唔係
   > `src/api/service.py` 嘅 —— 真檔案大三個數量級。用「相等 vs 少一 byte」呢個**關係**
   > 去講，先至係 mtime+size 失效規則真正靠嘅嘢，而且唔會隨檔案增長而過期；
   > 一個寫死嘅 size 讀數會（本 ticket 寫落之後 `service.py` 已經因為 CUI-0033 變大）。
   > 重量方法：`stat -c%s` 該檔案三次，每次只改嗰個 string literal。

> **S-069 更正（成因 vs 候選）**：本節原標題係「兩個都重現過」，讀落似係「成因已查明」。
> 「重現到一個機制」≠「當時真係發生咗呢個機制」，而 Lane E 嗰個 script 已經冇咗，
> 所以**原則上裁決唔到**。至少仲有第三個候選：**同一個 process 入面 re-import**
> （`sys.modules` 命中）。實測：寫新值落 `m.py` 之後再 `import m`，兩次（`"0"` 同 `""`）
> 都仍然讀到舊嘅 `':'`；即係話佢**三個 case 全部解釋得到**，包括 stale `.pyc`
> 解釋唔到嗰個 `""`，而且同 Lane E「輸出完全一樣」呢句更吻合。
>
> **所以防範措施唔綁成因，綁方法。** 常數 mutation 一律：
> (1) in-process `setattr` 改 module 物件、唔改源檔；(2) 改完即刻 `assert` 個值真係變咗；
> (3) 同一個獨立 oracle 比（`builder.downsample`），唔好同自己輸入嘅另一半比。
> 呢三項今次全部做咗，只係之前冇寫低。
