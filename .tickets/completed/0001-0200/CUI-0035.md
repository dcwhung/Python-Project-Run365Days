## 問題描述

Reviewer 喺 **S-066** 指出 `[tool.coverage.run] source = ["src"]` 令 `api/graphql.py`
（Vercel 入口）永遠唔入 coverage 分母，並評為「零現存風險」。
QA 核實影響嗰陣量到咗**被隱起嗰半究竟係乜**，結論比 S-066 嚴重一級。

### 量度（`.venv/bin/python -m pytest tests -q --cov=src --cov=api`）

| | statements | miss | cover |
|---|---|---|---|
| `api/graphql.py` | 44 | **23** | **48%** |
| TOTAL（`src` 加 `api`）| 1676 | 105 | 94% |
| TOTAL（今日記錄嘅 `src` only）| 1632 | 82 | 95% |

`api/graphql.py` 係**全 repo 覆蓋率第二低嘅檔案**（僅次於 `src/weight/analysis.py` 80%），
而佢係唯一一個 production deploy 入口。

### 冇覆蓋嗰 23 句係邊 23 句

`--cov-report=term-missing` 出：`45-52, 57-78, 89-90`

| 行 | 內容 | 佢存在嘅理由 |
|---|---|---|
| 45–52 | `_load_package_from_source()` 個 body（early-return 之後） | `run365days` 唔 importable 時由 `src/` 直接載，係 module docstring 講嘅「safety net」 |
| **57–78** | **`_error_app()` 全個 function** | module docstring：「If start-up fails, a minimal app still answers `/api/health` with the error so the cause is visible without digging through function logs」 |
| 89–90 | `_build_app()` 個 `except` 分支 | 唯一一條通往 `_error_app` 嘅路 |

即係話：**一個功能整份都係為咗「deploy 爛咗嗰陣仲睇得到點解爛」而存在，
本身冇一條測試行過，而且 config 保證咗冇一份 coverage report 會提起佢。**

`_error_app` 入面仲有第二層 fallback（連 Flask 都 import 唔到嗰陣嘅 raw WSGI app，行 62–78），
嗰層更加係「最壞情況下最後一道防線」。

### 點解特別值得補

CLAUDE.md §6 明文記住呢個檔案有兩個好脆嘅約束：

> 「唯一被認嘅 file name 係 `api/graphql.py`」、「`app = _build_app()` 必須係 top-level statement，唔可以入 try block」

`tests/test_api.py` 嘅 `VERCEL_ENTRY`（`:47`）確實有真正 `exec_module` 佢
（所以嗰 48% 係真正執行得嚟嘅覆蓋，唔係靜態掃描），但走嘅全部係 **happy path**。
`_build_app()` 一失敗，個 deploy 會回一個 500 JSON —— 而嗰個 500 JSON 嘅內容**冇人驗過**。

## 影響範圍

- **今日零 production 風險**：happy path 有測試，deploy 行緊。
- 風險係：呢條路徑**只會喺已經出事嗰陣行**，即係「最需要佢啱」嗰刻，
  亦都係「最冇機會發現佢爛咗」嗰刻。

## 建議修復方向（由 developer 判斷）

1. **補測試（本票主體）**：
   - monkeypatch `run365days.api.app.create_app` 掟 exception → `module.app.test_client().get(HEALTH_PATH)`
     應該回 500 同埋 body 入面有 exception 嘅 type name + message
   - 第二層：令 `flask` import 唔到（`sys.modules["flask"] = None`）→ 確認 raw WSGI fallback
     回 `500 Internal Server Error` + `Content-Type: application/json`
   - `_load_package_from_source()`：`find_spec` 回 `None` 嗰條路
2. **coverage 分母（= S-066 方案 A，可分開做）**：`source = ["src", "api"]`。
   ⚠️ 會令 TOTAL 由 `1632 / 82 / 95%` 變成 `1676 / 105 / 94%`，
   即係**動到 `.proj-docs/` 已記錄嘅每一個 coverage 數字** —— 呢個正正係 CUI-0032 刻意避開嘅事。
   **建議先做 (1)**：補完測試之後個 48% 會升，嗰陣先改分母，一次過搞掂，
   唔使為咗一個 48% 嘅數去改一堆歷史紀錄。
3. **最平嘅過渡（= S-066 方案 B）**：`pyproject.toml` 個 comment 加一句講明
   `api/graphql.py` 係刻意唔計、佢由 `tests/test_api.py` 嘅 `VERCEL_ENTRY` 守住。零數字變動。

### 對票上講法嘅更正（實測推翻）

1. **TOTAL 數字**：票寫「`src` only = 1632 / 82 / 95%」同「src+api = 1676 / 105 / 94%」。
   喺 base `6576e56` 實測係 **1652 / 81 / 95%** 同 **1696 / 81 / 95%**，兩個 statement 數都
   差 20。`api/graphql.py` 個 44 / 23 / 48% 同 missing `45-52, 57-78, 89-90` **逐個字啱**。
2. **「TOTAL 會由 95% 跌到 94%」冇發生**。票嘅預測假設分母改動**單獨**做；票自己建議嘅
   「先做 (1) 再做 (2)」正正令佢唔成立 —— 測試將 `api/graphql.py` 推到 0 miss，
   所以加分母只係 +44 statements / +0 miss，TOTAL 百分比**原地不動**。
   即係 `.proj-docs/` 引用緊嘅 **95%** 唔使改；要改嘅只係 statement / miss 兩個絕對數。
3. **「全 repo 覆蓋率第二低」唔成立**。實測排名（src+api）：`src/cli/export_schema.py` **0%**、
   `src/cli/collect_weather.py` **45%**、然後先至 `api/graphql.py` **48%** —— 係**第三低**。
   票講嘅參照 `src/weight/analysis.py` 80% 排第六，唔係鄰位。
   （「唯一一個 production deploy 入口」呢個理由本身唔受影響。）

### 測試真係能紅（mutation，按 CLAUDE.md §6 方法：assert mutant 生效，唔好假設）

每個 mutant 都先 `rm -rf api/__pycache__`，再用一個**獨立 oracle**（自己 `exec_module` 一次、
斷言 mutant 嘅可觀察後果）確認 mutant 真係喺執行緊嘅 bytes 入面，之後先睇 pytest：

| Mutant | Oracle 斷言 | pytest |
|---|---|---|
| `_error_app` 開頭加 `return None` | `module.app is None` → True | 3 條紅 |
| 刪走 `_load_package_from_source` 嘅 early `return` | installed module 被 rebind → True | `test_an_installed_package_is_left_alone` 紅 |
| 將 `_load_package_from_source` body 換成 `return` | rebind 冇發生 → True | `test_the_entry_registers_src…` 紅 |

第二個 mutant 順帶揭發咗一個會變假綠嘅寫法：editable install 之下
`run365days.__file__` **本身就係** `src/__init__.py`，所以單靠比對 path 分辨唔到
「載咗 src/」定「本來就係 src/」。已改成斷言 module **identity**（`loaded is not installed`）。
