## 問題描述

Vercel **唔係**由 GitHub Actions 部署嘅。`pages.yml` 綠代表 GitHub Pages 嗰邊 build 到，
同 Vercel 嗰個 serverless function 起唔起得到**完全冇關係**。今日 repo 入面冇任何嘢
喺部署之後 check 過 API。

呢個唔係假設出嚟嘅風險，`docs/deployment.md` §「What the first deployment taught」
一張表逐行記住六次失敗，每次都係**人手喺 Vercel Logs tab 度捉返出嚟**，其中兩種正正係
smoke test 應該接住嗰兩種：

| 失敗 | 今日點樣發現 |
|---|---|
| `ModuleNotFoundError: No module named 'flask'`（function 起唔到） | 人手睇 runtime log |
| export 寫咗個 **64 KB、0 個 activity** 嘅 database | 人手發現 |

## ⚠️ 設計上一定要解決嘅兩個陷阱

### (1) `/api/health` 回 200 唔代表冇事 —— 但**唔係**主票講嗰個理由

`api/graphql.py:24` 起唔到 app 嗰陣會起一個 minimal fallback app，**照樣答 `/api/health`**。
所以直覺會諗「淨係 ping health 分唔到真 app 定 fallback」。

**實測之下呢個講法唔準**：fallback 答嘅係 **HTTP 500** ＋ `{"status": "error", ...}`，
真 app 答 **200** ＋ `{"status": "ok", "db": ...}`。⇒ 單靠 status code 已經分得開，
一句 `curl --fail` 都捉到。

**真正 health 捉唔到嗰樣係另一件事**：DB **存在但空**。
`create_app` 只係 `make_engine`（檢查檔案在唔在），`health()` 回嗰個 `db` 係**路徑**唔係**行數**。
一個 0 activity 嘅 export 一樣 200 OK ——即係上面表入面嗰個 64 KB 事故。
實測：populated DB 同 empty DB **兩個都係 65536 bytes**，size 一樣分唔開。

⇒ **所以要夾一條真 GraphQL query**，而且要 assert 返嚟嘅**行數**，唔係 assert 200。

### (2) `deployment_status` trigger 喺呢個 repo 會靜英英完全唔行

Vercel **真係**出 GitHub Deployment（唔止 commit status）。實測 2026-09-17：
`GET /deployments` 100 條入面，`vercel[bot]` 開嘅有 `Production` 8 條、`Preview` 84 條，
淨低 8 條係 `github-pages`。`environment_url` 只有 Deployment 有，commit status 冇。

但 GitHub 規則：**`deployment_status` 只會用 default branch 上面嗰份 workflow file**。
本 repo default branch 係 `master`，而部署源頭係 `develop` ⇒ 一個寫成 `deployment_status`
嘅 workflow merge 落 `develop` 之後**一次都唔會行**，要等下次 release merge 上 `master`。
一個「由頭到尾唔行」嘅 gate 比一個「永遠綠」嘅 gate 更難發現。

⚠️ 同一條規則亦令 `schedule:` 唔用得（CUI-0052 個 audit workflow 已經明文記低咗同一個坑）。

⇒ 用 `push: develop`（冇呢個限制），自己 poll Deployments API 等 Vercel 報 success。

## 要求

1. **唔可以坐喺部署路徑上游** —— 呢張票同 CUI-0052 同一條線。紅咗只係一個紅 check，唔擋任何嘢。
2. **唔可以砌一個永遠綠嘅 gate**（`CLAUDE.md` §6 已經有兩次教訓）。交票之前要有**實測證據**證明
   佢喺壞嘅情況下真係紅。
3. 攞唔到 production URL 就要明文講缺咗咩，唔好亂估一個當數。

## 驗證方式

- 用一個本地起嘅真 app（populated DB）→ 必須綠
- 用 `api/graphql.py` 個 fallback app（指去一個唔存在嘅 DB）→ 必須紅
- 用一個 **meta 有、activities 空**嘅 DB → 必須紅（呢個 case 單獨驗到 row-count assertion 有力）
- 指去一個冇嘢聽 / 錯 base URL → 必須紅
- parsed YAML 核實：新 workflow **冇任何 job needs 佢**，而 `build.if` / `deploy.if` 冇郁

## 2026-09-17 —— 落地

### 交咗啲乜

| 檔案 | 作用 |
|---|---|
| `.github/workflows/smoke.yml` | `push: [develop]` ＋ `workflow_dispatch`（可傳 `base_url`）。一個 job，**冇任何嘢 needs 佢** |
| `scripts/wait_for_vercel.py` | Poll GitHub Deployments API，等 `sha` ＋ `environment=Production` 嗰個 deployment 報 success；報 `failure`/`error` 即刻紅，timeout（預設 900s）都係紅 |
| `scripts/smoke_api.py` | 打 `/api/health` ＋ 一條真 query，stdlib only |

打邊個 URL：**production alias**（`docs/deployment.md` 個表寫嗰個），唔係 deployment status
嗰個 per-deployment `environment_url`。理由：alias 先係讀者真正 load 嗰個 URL，而且 alias 先係
「有機會仲指住舊 build」嗰個 —— 打 immutable URL 會喺一個「冇人 access 到」嘅 deployment 上面轉綠。
`environment_url` 照樣 print 出嚟做對照。

### 偵測力實測（6/6）

`scripts/smoke_api.py` 直接對住本地起嘅 WSGI server 行，每個 case 都係一個完整 subprocess，
睇 exit code：

| Case | 期望 | 實測 | 邊個 assertion 捉到 |
|---|---|---|---|
| 真 app ＋ populated DB | PASS | **PASS**（exit 0）`meta.year=2021, activitiesCount=2` | — |
| 真 app ＋ 全空 DB（冇 meta row） | FAIL | **FAIL**（exit 1） | health **過咗 200 ok**，query 紅喺 `KeyError: 'year'` |
| 真 app ＋ **meta 有、activities 空** | FAIL | **FAIL**（exit 1） | health **過咗 200 ok**，`activitiesCount is 0, expected at least 1` |
| `api/graphql.py` 個 start-up fallback（DB 唔存在） | FAIL | **FAIL**（exit 1） | health：`HTTP 500, expected 200` |
| 冇嘢聽個 port | FAIL | **FAIL**（exit 1） | `URLError: Connection refused` |
| 健康 app 但**錯 base URL**（`/typo` 前綴） | FAIL | **FAIL**（exit 1） | 404 body 唔係 JSON |

⚠️ 中間兩個 case 就係**呢張票存在嘅理由**：health 兩次都**綠**，query 兩次都**紅**。
而且兩個 DB 檔案 `populated = 65536 bytes`、`empty = 65536 bytes` —— **size 一模一樣**，
即係話 `docs/deployment.md` 嗰個「64 KB、0 activity」事故用檔案大細係捉唔到嘅。

`scripts/wait_for_vercel.py` 對住**真嘅** GitHub API 行過兩個 case：

```
--sha 23733da…（真係 deploy 咗）  → state=success
                                   url=https://python-project-run365-days-mdnaez4ip-dcwhungs-projects.vercel.app
                                   exit 0
--sha 763d91a0000…（唔存在）      → "no production deployment for this commit yet" ×2 → timeout → exit 1
```

### 冇做嘅嘢，同點解

- **冇打 GitHub Pages 嗰邊。** roadmap 寫嘅係「the deployed API」，而 Pages 嗰邊冇 API。
  而且 Pages 嗰個 deploy 本身就係喺 `pages.yml` 入面由 `actions/deploy-pages` 做，失敗會直接紅；
  Vercel 嗰邊先係**完全冇 in-CI signal** 嗰半。（`VITE_BASE_PATH` regression 值唔值得單獨加個
  Pages check 係一個獨立問題，留返。）
- **冇自動開 issue / 送通知。** 紅係一個 commit 上面嘅紅 check ＋ Actions tab ＋ GitHub 自己嗰個
  failed-run 通知。同 `audit.yml` 一致，而且本 repo **冇 branch protection**（實測
  `develop` / `master` 兩邊 `"protected": false`），所以「有人見到紅」本來就係全部嘅強制力。
- **冇用 `deployment_status`。** 見上面陷阱 (2)。

### 一個落地之後先驗證到嘅風險（明文記低）

寫呢張票嗰個環境 **去唔到 `*.vercel.app`**（egress proxy 擋咗，`connect_rejected`），
所以 `https://python-project-run365-days.vercel.app/api/health` **未親手打過**。
`scripts/smoke_api.py` 嘅偵測力係對住本地起嘅同一個 Flask app 驗嘅，呢部分係實測；
但「個 alias 今日真係咁樣答」呢一步要靠 merge 之後第一個 run 確認。
如果第一個 run 紅，先睇 log 入面嗰個 `Deployment URL:` 同 `BASE_URL` 係咪唔同一個 host —— 
最可能嘅原因係 alias 改咗名，唔係 code 有 bug。
