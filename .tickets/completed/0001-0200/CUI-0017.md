## 問題描述

`src/api/schema.py:84`：

```
Worst case is therefore 64 x 2 = 128 statements. Batching the per-activity
queries (AU-050) would let this number be raised on its own, without
reopening the points budget.
```

「Worst case is therefore 128 statements」讀落係**一個 request 最壞情況嘅語句數**，
但 128 只計咗 `track` field 嗰半。實測一個 request 可以去到 **208 條**。

差額嚟自 `activity(id:)` 呢個 **nullable** root field：

- `activity(id:)` 回 `Activity | None`，係 nullable，所以一個被拒嘅 `track`
  **只會將自己嗰個 alias 變 null，個 request 會繼續行落去**
  （唔似 `activities: [Activity!]!` 會 non-null propagate 到 root 一次過收工）。
- 每個 aliased `activity(id:)` parent **本身就要 ~2 條語句**
  （`session.get` + `selectinload(warnings)`），**而且無論佢個 `track` 有冇被拒都照收費**。
- 呢半邊**唔受 `MAX_TRACK_FIELDS_PER_REQUEST` 約束**，只受 `MAX_QUERY_TOKENS = 1000` 約束。

## 重現步驟

以真實 export（365 activities）起 `create_app`，用 `before_cursor_execute` 數語句，
二分搜尋出 token limiter 容許嘅最大 alias 數，然後發呢個 document：

```graphql
query { x0: activity(id: "<id>") { track(points: 1) { sec } }
        x1: activity(id: "<id>") { track(points: 1) { sec } }
        ...  # 共 52 個 alias，啱啱好喺 MAX_QUERY_TOKENS = 1000 之內
}
```

實測輸出：

```
max aliases accepted by the token limiter : 52
tracks served                             : 52 (field cap = 64)
tracks refused                            : 0
TOTAL SQL                                 : 208   wall 143 ms
breakdown: 52 parent lookups x 2 = 104, plus 52 served tracks x 2 = 104  -> 208
```

多跑 10 次：p50 = 137 ms、max = 174 ms。

## 預期結果

Docstring 講嘅 worst case 同實測對得上；如果 128 係特指 `track` 嗰半，就講明係嗰半。

## 實際結果

Docstring 寫 128，實測 request 層面 208（1.6×）。

## 建議修復方向

二選一：

1. **收窄語句**（最細改動）：
   「Worst case for the `track` fields themselves is 64 x 2 = 128 statements.」
   再補一句講明 nullable parent（`activity(id:)`）嘅 fan-out 由 `MAX_QUERY_TOKENS` 約束，
   實測整個 request 上限約 208 條 / <200 ms。
2. **連埋講埋整體**：直接寫 request 層面嘅實測 worst case（208 / 174 ms / 86× headroom），
   因為呢個先係讀者真正想知嘅數。

⚠️ 唔建議改代碼收緊 —— 現有 bound 完全足夠，收緊只會無謂噉削合法用法。

## 解決方案

**文件部分已由 `2a043f7`（AU-050）＋ `bc0a7ca`（S-034 / S-035）完成，本次只補測試。**

逐句核實 `MAX_TRACK_FIELDS_PER_REQUEST` 現行 docstring，同本票實測對得上，無需改動措辭：

- 「at most 64 batches of 2 = 128 of them」已明文收窄成**只講 `track` statements**，
  即票上建議方向 1。
- 「It is not a bound on the statements a request issues … every parent field
  carrying a `track` costs about two statements of its own first … That half of
  the cost is bounded by `MAX_QUERY_TOKENS` alone」已交代 nullable parent fan-out。
- 「52 parents naming 52 *different* activities cannot share and issue 208
  (52 x 2 + 52 x 2)」同本票實測 208（52 parent lookups x 2 + 52 served tracks x 2）逐項一致。

補做本票「驗證方式」嘅可選項 —— 一條釘住 **request 層面**語句上限嘅測試：

`tests/test_api.py::test_a_flood_of_aliased_parents_issues_more_statements_than_the_field_cap_bounds`

- 用 aliased `activity(id:)` shape（**唔係** `activities`），同
  `test_the_alias_flood_issues_no_more_statements_than_the_field_cap_allows` 對稱。
- parent 闊度由 `_widest_parent_flood()` **推導**（唔 hard-code 52），token limit 一郁就會紅。
- 斷言 `sql_count > MAX_TRACK_FIELDS_PER_REQUEST * SQL_PER_TRACK_BATCH`
  —— 即實測 208 > cap 單獨計嘅 128，正正係本票開票嘅偏差。
- 再斷言 refused 嗰半：52 個 parent 每個 `track(points: MAX_TRACK_POINTS)`，
  points budget 拒絕大部分 track，但 parent 嗰兩條語句照收，
  錯誤訊息逐條核實係 `MAX_TRACK_POINTS_PER_REQUEST` 所拒（唔係 field cap）。
- `_distinct_parent_flood` 加 `points` 參數（INT 係一個 token，token 成本不變，
  所以 parser 唔會搶住拒絕）。

Docstring 只加一句，指返新測試做佢嘅 gate（repo 慣例：寫低嘅數字要有 assertion 撐）。

**TDD 紀錄**：🔴 先將 `ceiling` 改成 cap 單獨計嘅 128 跑一次，
得到 `assert 208 <= 128` 嘅 **AssertionError（Fail，唔係 collection Error）**，
證實測試真係量到 request 層面成本；🟢 再還原推導式 ceiling 轉綠。
