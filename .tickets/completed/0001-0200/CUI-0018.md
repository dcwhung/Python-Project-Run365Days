## 問題描述

兩個獨立但同屬「budget 拒絕嘅 client 體驗」嘅缺口。

### (a) 錯誤冇機器可讀嘅分類

Budget 拒絕回嘅 error object 只有三條 key：

```json
{"data":null,"errors":[{
  "message":"track field budget exhausted: one request may read at most 64 tracks",
  "locations":[{"line":1,"column":61}],
  "path":["activities",64,"track"]}]}
```

```
keys : ['locations', 'message', 'path']
```

**冇 `extensions`，冇 `code`。** Client 想分辨「我個 query 太貪心，減少數量再試」
同「server 壞咗，唔好再試」，唯一辦法係 **match `message` 字串**。
而個訊息係由 `MAX_TRACK_FIELDS_PER_REQUEST` f-string 嵌入常數值砌出嚟，
常數一改字串就變 —— client 嘅 string match 會靜靜哋失效。

> 好消息（已核實）：response **冇洩漏任何 internal detail** ——
> 177 bytes、無 stacktrace、無絕對路徑、無 context key 名。
> W-013 特登唔講出 `track_points_remaining` 呢個 key 係做得啱嘅，本票唔推翻嗰個決定。
> 至於 server 端 log 仍然有完整 traceback，屬 **S-014 / S-018** 範圍，唔喺本票。

### (b) 一個被拒 `track` 會連兄弟 field 一齊清空

`activities: [Activity!]!` 同 `track: [TrackPoint!]!` 都係 non-null，
所以一個被拒嘅 `track` 會 non-null propagate 一路上到 root：

```graphql
query { meta { year }
        activities(limit: 65, hasGps: true) { id distanceKm track(points: 1) { sec } } }
```
→ `data: null`。**連完全成功嘅 `meta` 都冇埋。**

對比 nullable parent 就溫和得多：`activity(id:)` 之下被拒，`data: {"a": null}`，兄弟照返。

呢個係 GraphQL non-null 語義嘅必然結果，**唔係 AU-047 造成**，而且今日前端
（一個 request 只有 1 個 `track` field）撞唔到。但 AU-050 之後多 track 嘅 view 會變常態。

## 實際修復（實測，唔係計劃）

### (a) — 四個 code，按「client 要改咩」分，唔係按 exception class 分

| code | 幾時 | client 要做咩 |
|---|---|---|
| `LIST_ROW_BUDGET_EXCEEDED` | list field 一次開太多 row | 細啲嘅 `limit`，或者少啲 list field |
| `TRACK_POINTS_BUDGET_EXCEEDED` | 所有 `track` field 加埋要太多 sample | 細啲嘅 `points`，field 數目唔使變 |
| `TRACK_FIELD_BUDGET_EXCEEDED` | `track` field 太多 | 少啲 `track` field；**細 `points` 幫唔到手** |
| `ARGUMENT_OUT_OF_RANGE` | argument 超出 SDL 講明嘅範圍 | 改個值；原封不動再 retry 永遠唔會得 |

三個 budget code 而唔係一個，係因為三個補救唔同：一個 `track` field 無論 `points` 幾細
都係同一條 query，所以「淨係話你太貪心」會令 client 扭錯個掣。Bounds 只得一個 code，
因為每次補救都一樣，而且 `path` / `locations` 已經指到邊個 **field**。

> **更正（W-035）**：原文呢句寫住「已經指到邊個 field 邊個 argument」，**argument 嗰半係假嘅**。
> `ClientRefusalError` 傳 `nodes=raw.field_nodes`，所以 `locations` 永遠指住 field name。
> 實測 `{ activities(limit: 1000, offset: -1) { id } }` 同 `{ activities(limit: -5, offset: 0) { id } }`
> 兩條 query **`path` / `locations` 完全一樣**（`["activities"]`、line 1 column 3），
> 只有 `message` 唔同。對 `track` 冇影響（`points` 係佢唯一 argument）；
> 對四條 list field（各有 `limit` 同 `offset`）就係一個知情保留嘅窿 —— client 要分辨邊個
> argument 就仍然要 parse message。將來要補係加 `extensions.argument`，唔係加多兩個 code。
> 同一句錯嘅措辭亦喺 commit `3ee16c3` message 入面（歷史，改唔到）。

`code` 係 constructor 嘅必填參數，唔係 class attribute 亦唔係喺 `process_errors` 統一貼上去：
class attribute 會令新 subclass 靜靜地繼承錯嘅分類；統一貼要從 message 反推原因
（正正係本票要 client 唔好做嘅事），而且會令 server fault 睇落同「你可以縮細再試」一樣。

W-013 嘅決定原封不動：`extensions` 入面**淨係**得個 code。有測試讀 raw response text，
撞到 `track_points_remaining` / `track_fields_remaining` / `list_rows_remaining` 就紅。

### (b) — `track: [TrackPoint!]`（breaking）

**實測 base `06ad4bd`**：票上嗰條 document 回 `data: null` —— 64 條已經讀咗兼付咗錢嘅 track、
一個完全冇掂過 budget 嘅 `meta`，client 一樣都攞唔到。而家第 65 個 `track` 係 `null`，
error 喺 `errors` 旁邊，其餘全部照返。

Element 保持 non-null（`[TrackPoint!]` 而唔係 `[TrackPoint]`）：被拒唔會令某一個 **sample**
唔見咗，served 嘅 track 係完整嘅。

**冇擴大**去 list field：`activities` 仍然係 `[Activity!]!`，被拒嘅 page 照樣清空成個
response —— 一個被拒嘅 page 根本冇 field 可以收個 null。有測試釘住呢條界，
令將來想擴大係一個睇得見嘅決定。
