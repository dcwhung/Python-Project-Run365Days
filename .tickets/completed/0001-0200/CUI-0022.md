## 問題描述

`src/common/time.py:167` 嘅 `activity_time_range(start, end, period=30)` 係一個
public（無底線前綴）module-level function，有完整 Google-style docstring，
**但係全 repo 冇任何 caller**。

```
$ grep -rn "activity_time_range" src/ tests/ frontend/ legacy/
src/common/time.py:167:def activity_time_range(start: datetime, end: datetime, period: int = 30):
```

唯一命中就係佢自己嘅定義。`legacy/`（2022 舊 script）都冇用。

Coverage（`pytest --cov=src`，363 passed）：

```
src/common/time.py    44    3    93%   178-182
```

三條未覆蓋嘅 line（178 / 179 / 182）**全部**係 `activity_time_range` 嘅 body，
即係話呢個 function 係成個 module 裡面唯一冇被測試行過嘅嘢，
而佢冇被行過嘅原因就係冇人叫佢。

## 影響

**今日零功能影響** —— 冇 caller 就冇行為。成本喺兩度：

1. **Coverage 訊號被溝淡。** `time.py` 報 93.2% 而唔係 100%，令人以為
   `parse_datetime` 有未測試嘅路徑。實測 `parse_datetime` 四條分支全部有覆蓋
   （包括 CUI-0006 新加嘅 `_ISO_OFFSET_PATTERN.search` L119 同 `.astimezone(tz)` L126）。
2. **佢有 docstring 同 type hint，睇落係現役 API。** 下一個讀 `time.py` 嘅人
   要自己 grep 一次先知佢係死嘅。

另外佢**未經測試**：`ceiling` 用 `end.minute // period + 1`，喺 `end.minute`
啱啱好係 period 邊界（例如 30）嗰陣會推到下一個鐘，呢個係咪 intended
冇任何 assertion 講過。所以佢亦唔係「安全嘅備用工具」—— 邊個第一個用佢，
邊個就係第一個測佢。

## 建議

三選一，由 owner 決定（QA 唔代拍板）：

| 方案 | 做法 | Trade-off |
|---|---|---|
| **A（推薦）** | 刪走佢。git history 留住咗，真係要用可以 revert 返出嚟 | 最乾淨；`time.py` 去到 100%，coverage 訊號變得可信 |
| B | 補測試，保留 | 要為一個冇 caller 嘅 function 定義同釘死語意（尤其係上面講嘅 period 邊界），成本唔細而買唔到功能 |
| C | 加 `# pragma: no cover` + 喺 docstring 寫明「currently unused」 | 最平，但留低一個永遠唔會被驗證嘅 public function，同 repo「寫低嘅嘢要有 assertion 撐」嘅慣例相反 |
