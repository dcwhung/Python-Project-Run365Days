## 問題描述

CUI-0008 喺 `src/common/geo.py` 加嘅 guard 只 reject `±inf` / `nan`。**範圍完全冇檢查。**

QA 實測：

| 輸入 | 結果 |
|---|---|
| `lat=400` | **4447.8 km**（理直氣壯回一個數）|
| `lat=91` | **10118.7 km** |
| `lat=lon=1e20` | **5560.1 km** |
| `lat=lon=1e308` | **`nan`** + `RuntimeWarning: invalid value encountered in sin` |

⚠️ `parse_finite_float("1e308")` **照收**（佢真係 finite），而 `pandas.Series([1.0, nan, 2.0]).sum() == 3.0`
—— 即係 **CUI-0001 / CUI-0008 立項要消滅嗰個「nan 靜靜哋跌出總和、距離報細咗」嘅形狀，
由一道 guard 冇 cover 嘅門返咗嚟**。

## 影響

🟢 Low。要 `1e308` 級數先至出 `nan`。但 `lat=400` 呢類「合理咁錯」嘅值一早已經冇人查
（例如 unit 搞錯、經緯度掉轉、或者某個 device 出 raw sensor value）。

## 建議

喺現有 guard 加範圍檢查：`-90 <= lat <= 90` / `-180 <= lon <= 180`，掟同一個 `ValueError`。
`parse_all` 已經有 `ValueError` 分支（`base.py:207`），唔使動 layering。

⚠️ 留意佢係 hot path（`total_track_distance` 逐點呼叫）—— 檢查要**向量化**，
同 CUI-0008 個 guard 一齊做，唔好多加一次 Python-level loop。CUI-0008 實測 guard
只佔一段端到端成本 0.65%，加範圍檢查之後要重量一次。

## 驗證方式

- `hav((400,0),(0,0))` / `hav((0,200),(0,0))` / `hav((1e308,1e308),(-1e308,-1e308))` 三個都要 raise
- **現有 357 條 GPS activity 嘅 export 結果逐 byte 不變**（呢個係最重要嗰條 —— 唔可以有真數據被拒）
- Hot path 前後量度（交錯 A/B、fresh process、median of 5）

## ✅ 完成紀錄（2026-09-17，base `77868dd`，branch `fix/common/CUI-0047_reject-impossible-coordinates`）

### 改動

`src/common/geo.py:100` —— guard 由 CUI-0008 嘅四個 `math.isfinite` 換成四個範圍測試：

```python
if not (abs(lat1) <= 90.0 and abs(lon1) <= 180.0 and abs(lat2) <= 90.0 and abs(lon2) <= 180.0):
```

係**取代**唔係**疊加**：`abs(nan)` 係 `nan`，而 `nan` 同任何嘢比較都係 `False`；`inf` 過唔到
`<= 90.0`。所以有限性檢查被範圍檢查吞埋，唔使行兩次。Raise path 先再分辨係邊種失敗，
出 `non-finite coordinate` 定 `out-of-range coordinate`（兩個都係 `ValueError`，
`parse_all` 嗰個 `ValueError` 分支照食，layering 冇郁）。

Bounds 係 **inclusive**：南北極同 antimeridian 係真地方，`<` 會拒 `(90, 180)`。
