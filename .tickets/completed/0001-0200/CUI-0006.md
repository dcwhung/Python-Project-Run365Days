**建立日期**：2026-09-14
**負責人**：Backend Developer

## 問題描述

`src/common/time.py` 嘅 `parse_datetime(rec_time, timezone="Asia/Hong_Kong")` docstring 寫明：

> Returns: A timezone-aware ``datetime`` in ``timezone``.

但 ISO-with-offset 分支（`elif "+" in rec_time:`）直接 `return dateutil.parser.parse(rec_time)`，
**冇 `.astimezone(tz)`**，所以個 `timezone` 參數對呢條路徑完全無效 —— 永遠攞返**輸入字串自己**嘅 offset。

## 重現步驟

```python
from run365days.common.time import parse_datetime

# ISO with offset — timezone 參數被無視
for tz in ["Asia/Hong_Kong", "America/New_York", "UTC"]:
    print(tz, parse_datetime("2021-10-17T06:10:56+08:00", tz))

# 對照組：naive 輸入正常跟參數
for tz in ["Asia/Hong_Kong", "America/New_York", "UTC"]:
    print(tz, parse_datetime("2021-10-17 06:10:56", tz))
```

## 實際結果

```
ISO-with-offset（全部一樣，參數無效）
  Asia/Hong_Kong     -> 2021-10-17 06:10:56+08:00
  America/New_York   -> 2021-10-17 06:10:56+08:00
  UTC                -> 2021-10-17 06:10:56+08:00

naive（正常跟參數）
  Asia/Hong_Kong     -> 2021-10-17 06:10:56+08:00
  America/New_York   -> 2021-10-17 06:10:56-04:00
  UTC                -> 2021-10-17 06:10:56+00:00
```

四條 input path 之中，只有 ISO-with-offset 呢條唔遵守 `timezone` 參數。

## 預期結果

跟 docstring：回傳值應該轉換到 `timezone`，即
`dateutil.parser.parse(rec_time).astimezone(tz)`。
（注意：呢個係**轉換**，唔會改變絕對時刻，只改變表示嘅 offset。）

## 影響範圍

**目前生產零影響**：全部 caller 都用預設 `timezone="Asia/Hong_Kong"`，而所有真實 Garmin
ISO-with-offset 時間戳本身就係 `+08:00`，所以「輸入 offset」啱啱等於「要求 offset」，
撞啱同結果。現有測試 fixture 全部係 `+08:00`，所以測試亦係撞啱綠。

風險喺於：任何人第一次傳一個非 HK 嘅 `timezone` 落去，會靜靜咁攞到錯嘅 offset，
而且冇任何測試會 fail。

## 與其他 ticket 嘅關係

- **AU-003**（已完成）修嘅係 `.replace(tzinfo=)` 嘅 LMT 問題，唔涉及呢條分支
- **AU-048**（pending）修嘅係 Unix-ms 分支早 8 小時，亦唔涉及呢條分支
- 三者同屬 `parse_datetime` 嘅 input path 一致性問題，**建議一併處理**

## 建議修復方向

`elif "+" in rec_time:` 分支加 `.astimezone(tz)`，並補測試斷言三個唔同 `timezone`
參數下嘅 offset 各自正確。做嗰陣順帶檢查 `"-"` offset（例如 `-05:00`）有冇被
`"+" in rec_time` 呢個條件漏咗 —— 睇落係漏咗，會跌落最後嗰句 `strptime` 而 raise。

## 驗證方式

- 上述重現 script 三個 timezone 各自回唔同 offset 而絕對時刻相同
- 188 條現有測試仍然全綠

## 解決方案

### 改咗乜

`src/common/time.py`：

1. **ISO-offset 分支加 `.astimezone(tz)`** —— offset 由「輸出標籤」降級成「用嚟決定係邊個絕對時刻」，
   之後一律換算落 *timezone*，同 `Z` / epoch-ms 兩條 instant path 睇齊。
2. **分支條件由 `elif "+" in rec_time` 換成 anchored regex `_ISO_OFFSET_PATTERN = re.compile(r"[+-]\d{2}:?\d{2}$")`** ——
   負 offset（`-05:00`）由「跌落最後嗰句 `strptime` 掟 `ValueError`、成個檔案 parse 唔到」變成正常支援。
   Regex **必須** anchor 喺字串尾：`"-" in rec_time` 會中晒每個 timestamp 嘅日期分隔號，
   呢個正正係當初條件只可以測 `"+"` 嘅原因。
3. **`Returns:` docstring 重寫** —— 原文寫住 offset「as written… never converted to *timezone*」，
   呢段已經係錯，改成「四種 supported form 全部回 *timezone*」。

`tests/test_common_time.py`：

4. **`TestParseDateTimeOffsetIsReturnedAsWritten` 整個改寫成 `TestParseDateTimeIsoOffsetIsConvertedToTimezone`** ——
   舊 class 係特登釘住舊行為嘅，class docstring 自己寫明「a future `.astimezone()` would turn red」同
   「belongs to its own ticket」。嗰張票就係本票，所以係重寫個 pin，唔係繞開佢。
   新增覆蓋：`+09:00` / `-05:00` / `+00:00` × `Asia/Hong_Kong` / `America/New_York` / `UTC`，
   斷言「絕對時刻相同、offset 跟參數行」。

### 負 offset 點處理

當作同正 offset 完全一樣嘅 instant 輸入：讀個 offset 決定係邊一刻，然後換算落 *timezone*。
`2021-10-17T06:10:56-05:00` → HK `2021-10-17T19:10:56+08:00`。改動前呢個輸入會 raise `ValueError`。

### byte-identical 驗證結果

改動前後各跑一次 `run365-activities --format kml|gpx|tcx`（真實數據 365×3 檔案），
再加一個連 **每一個 track point** 都 dump 出嚟嘅深度比對（1,087 個 activity record + 全部 track point）：

| 產出 | 結果 |
|---|---|
| `data/processed/activities_kml.jsonl`（357 records） | byte-identical |
| `data/processed/activities_gpx.jsonl`（365 records） | byte-identical |
| `data/processed/activities_tcx.jsonl`（365 records） | byte-identical |
| 深度 dump（activity + 全部 track point） | byte-identical |

零影響嘅原因實測核實過：KML 194,008 個時間戳 **全部** 係 `+08:00`（`sort | uniq -c` 得一行），
而香港冇夏令時間，所以 `+08:00 → astimezone(Asia/Hong_Kong)` wall clock 不變。

### 刻意唔做：`Z` 冇 milliseconds

`2021-10-16T22:10:56Z` 今日仍然跌落 naive branch 掟 `ValueError`，本票不處理。
理由：係另一條 branch、數據入面完全唔存在（實測 GPX + TCX 235,070 個 `Z` 時間戳，
**零個** 冇 milliseconds），而且現行 docstring 本身已經明文講「not supported」，所以文檔仍然誠實。
已加 `test_a_utc_z_string_without_milliseconds_is_still_not_supported` 釘住呢個狀態，
令佢係一個有紀錄嘅決定而唔係一個假設。
