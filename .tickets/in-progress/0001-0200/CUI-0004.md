## 問題描述

W-010 令 SQL 側嘅 stride 同 in-Python `downsample()` 完全一致（實測 0 分歧，見下）。
但 `points = 1` 呢個邊界之下，實際行為同 `_even_positions` 自己個 docstring 對唔上。

`src/api/service.py:136-152`：

```python
def _even_positions(total: int, points: int) -> list[int]:
    """...
    Returns:
        Strictly increasing positions, first and last row included.   <- 承諾
    """
    if points < 2:
        return [total - 1]            # <- line 150：只回最後一點，first 唔喺度
    ...
```

`points = 1` 時回 `[total - 1]`，即**淨係最後一點**，first row 唔包括在內。
GraphQL field description 亦寫「evenly downsampled to at most `points` samples」，
一個 sample 而家係「最後一個」而唔係「第一個」或者任何「evenly」嘅語義。

行為本身係**刻意**同 `run365days.dashboard.builder.downsample()` 對齊
（`if limit < 2: return [points[-1]]`），而個 module docstring 亦明講要對齊，
所以唔應該亂改行為 —— 但 docstring 嘅承諾同實際唔一致，係要修嘅嘢。

加上 coverage 顯示 **`src/api/service.py:150` 係成個 module 唯一冇被測試行過嘅 line**
（service.py 84 stmts / 1 miss / 99%）。即係話呢條同 docstring 矛盾嘅分支，
剛好亦係冇測試釘住嘅嗰條。

### 實際改動（三項，零行為改動）

1. **`src/api/service.py` — `_even_positions` docstring**
   由「Strictly increasing positions, first and last row included」改成分開講清楚：
   `points >= 2` 先保證首尾都在；`points == 1` 容納唔到兩者，回**最後一行**而唔係
   第一行，並註明呢個係刻意同 `run365days.dashboard.builder.downsample` 嘅
   `limit < 2` 分支對齊（兩個 sampler 喺兩個 deployment mode 撐同一個 field，
   每個 input 都要一致，包括呢個邊界）。

2. **`src/api/schema.py` — `TRACK_DESCRIPTION`**
   喺「evenly downsampled to at most `points` samples」之後補一句：
   `points: 1` 冇嘢可以 space evenly，回 track 嘅**最後一行**而唔係第一行。
   SDL 有改動，已跑 `run365-schema > frontend/schema.graphql` 同步，
   `run365-schema --check` 綠。

3. **`tests/test_api.py` — `test_a_single_sample_is_the_last_row_not_the_first`**
   斷言 `service.track(..., 1)` 回**一行**、而且係**最後一行**，
   並且等於 `downsample(range(600), 1)`（同時釘住「刻意對齊」呢個 claim）。
