# CUI-0014 from_raw_row() 對缺失 STRING 欄位預設 ""，舊 code 出 None

**狀態**：in-progress
**類型**：behaviour-change（需 reviewer 確認）
**優先級**：🟢 Low
**來源**：CUI-0011 修復過程中由 Backend Developer 主動申報
**建立日期**：2026-09-14
**負責人**：Backend Developer

---

## 問題描述

CUI-0011 嘅 `from_raw_row()` 將**缺失嘅 string 欄位**預設做 `""`，而舊 code 出 `None`：

- `HourlyWeather.description`
- `WeatherWarning.type` / `start_time` / `end_time`

Developer 嘅理由：令 dataclass annotation 保持誠實嘅 `str`，而唔使將五個欄位放寬成 `str | None`。

## 可達性

**實務上不可達。** Developer 掃過已 commit 嘅全部資料：17,984 個 hourly 行同 461 個 warning 行，
**每個檔案剛好得一個 distinct key set** —— 即係每一行都帶齊所有欄位。現有測試亦冇一條測缺失欄位。

對 byte-identical export **零影響**（已驗證）。

## 為何仍然開票

`""` 同 `None` 喺下游語意唔同：`if not value` 兩者都 truthy-false，但 `value is None` 只捉到一個，
而 JSON 輸出 `""` vs `null` 亦唔同。呢個係**靜默嘅行為收緊**，應該由 reviewer 明確接受或者推翻，
唔應該因為「而家撞唔到」就當冇發生。

## 兩個方向

- **接受現狀**：喺 `from_raw_row()` docstring 明確寫低「缺失 string 欄位 → `""`」，並加測試釘死
- **還原**：五個欄位改成 `str | None`，缺失時出 `None`（同舊行為一致），代價係 annotation 冇咁乾淨

## 驗證方式

- 無論揀邊個，加一條測試明確覆蓋「string 欄位缺失」呢個 case
- 283 條現有測試全綠
- static JSON 仍然 byte-identical

---

## 解決方案

**揀咗「接受現狀」** —— 缺失 string 欄位繼續讀成 `""`，唔還原做 `None`。用戶已拍板：
dataclass annotation 保持誠實嘅 `str`，唔使將五個欄位放寬成 `str | None` 去描述一個
實務上不可達嘅 case。**無改任何行為，純粹係文件化 + 測試釘死。**

### 點記錄（`src/weather/models.py`）

- `_MISSING_TEXT` 常數加 docstring：講明「缺失 string 欄位 → `""` 而唔係 `None`」、
  點解咁揀（保持 `str` annotation）、同舊 pre-CUI-0011 reader 出 `None` 嘅分別，
  以及呢個只 apply 落 *readings*，唔 apply 落 date。
- `HourlyWeather.from_raw_row()` docstring：明確寫低 `Time` / `Description` 缺失讀成
  `_MISSING_TEXT`，係刻意收緊，並點出 `""` vs `None` 喺下游唔等價
  （`value is None` 只捉到一個、JSON 出 `""` vs `null`）。
- `WeatherWarning.from_raw_row()` docstring：五個 text column 同樣處理，附 461 行實測依據。
- `DailyWeather.from_raw_row()` docstring：順手記低呢度**唔會**出現同類情況 ——
  佢宣告嘅 reading 全部係 `float | None`，缺失本身就係 `None`，冇 string 欄位可以 default。

### 加咗嘅測試（`tests/test_weather_models.py`）

新 class `TestMissingStringColumnsReadAsEmptyText`，class docstring 講明呢個係刻意行為、
日後有人改返 `None` 會喺呢度 fail：

- `test_hourly_from_raw_row_reads_a_missing_string_column_as_empty_text`
- `test_warning_from_raw_row_reads_a_missing_string_column_as_empty_text`

兩條都**實測過係 load-bearing**：暫時將 `_MISSING_TEXT` 改成 `None` 行一次，
兩條都出真正嘅 `AssertionError`（唔係 collection Error），之後即刻還原。

### `date` 欄位 KeyError 嘅判斷：**刻意，保留，並已寫入 docstring**

三個 `from_raw_row()` 嘅 `date` 都用 `row[RAW_DATE_COLUMN]`（**冇** `.get()`），缺失即 `KeyError`。
核實過呢個同其他欄位唔一致係有理由嘅 —— date 係行嘅**身份**而唔係 reading：

- `export/records.py` 三個 record shaper 都將 `date` 當 join key 出落 export；
- `dashboard/builder.py` 嘅 `nearest_hourly()` 早喺 `from_raw_row()` 之前就
  `r.get(RAW_DATE_COLUMN) != date` filter 咗，冇 date 嘅行根本到唔到；
  `warnings_by_date()` 一樣用 `r[RAW_DATE_COLUMN]` fail fast。

即係話缺 date 就係壞檔案，fail fast 好過 default 成 `""` 然後靜靜生成一條 key 係空字串嘅
垃圾 record。**冇改佢**，只喺 docstring 講明點解 key column fail fast 而 readings 降級。
