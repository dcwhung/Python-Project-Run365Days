## 問題描述

AU-001 加咗 `QueryDepthLimiter(max_depth=5)` 作為 query cost 防護。實測證實：

- 呢個 acyclic type graph **最深只到 depth 4**
  （`year → personalBests → longest → track|weather → leaf`）
- `QueryDepthLimiter` 要 `max_depth=3` 先開始拒絕嗰條 depth-4 document

即係話 `max_depth=5` 同 `max_depth=4` 對現行 schema 完全無分別，
呢層防護今日**一次都唔會 fire**。

`MAX_QUERY_DEPTH` 個 docstring 本身有講到呢點（「5 leaves one level of headroom」），
所以唔係寫錯，而係兩件實際後果：

1. AU-001 講嘅「depth limit」對今日嘅攻擊面提供零保護；真正擋住 alias flood
   嗰個係 `MaxTokensLimiter`（實測喺 ~1000 token 正確 fire）
2. **冇任何測試可以透過 public schema 行過呢條 branch**。要驗證只可以
   `build_schema(max_depth=<lower>)` 自己整一個 schema —— 現行 185 條測試冇做

## 重現步驟

```
### depth limiter 機制（build_schema 調低 max_depth）
  max_depth=5: d4=pass    d3=pass    d2=pass
  max_depth=4: d4=pass    d3=pass    d2=pass
  max_depth=3: d4=REJECT  d3=pass    d2=pass
  max_depth=2: d4=REJECT  d3=REJECT  d2=pass
  max_depth=1: d4=REJECT  d3=REJECT  d2=REJECT
```

`d4 = {year{personalBests{longest{track{sec}}}}}` —— 呢個 schema 砌得出最深嘅 document。

## 預期結果

一係將 limit 收到真係會 fire 嘅位（`max_depth=4`，即容許今日最深嗰條、拒絕再深一層），
一係喺註釋同 review 記錄講清楚「今日純屬 headroom，唔提供現行保護」，
並且加一條用 `build_schema(max_depth=...)` 嘅測試釘死個 limiter 真係接得上。

## 實際結果

Limit 設喺一個 unreachable 嘅值，無測試覆蓋，`src/api/schema.py` 雖然報 100% coverage
（`build_schema` 條 line 行過），但**行為分支**從來冇被斷言過。

## 解決方案

### 決策：`MAX_QUERY_DEPTH` 維持 5（用戶拍板）

票上「預期結果」給咗兩條路（收到 4，或者講清楚係 headroom 並加測試）。**用戶揀咗後者**：
常數值不變，改為喺 docstring 講明呢個選擇，並用測試釘死佢。

理由（已寫入 docstring）：graph 仲係呢個形狀嘅時候，留 headroom 唔使成本，
而且令「加一個 nested field」淨係一個 schema 改動，唔使順帶開限制討論。
代價係個 limit 會喺無人為意之下由 unreachable 變 reachable —— 所以要有測試接住。

### `src/api/schema.py`：`MAX_QUERY_DEPTH` docstring 重寫

- 明文寫 **「this limiter cannot fire against the schema as it stands」**，
  並講明係刻意選擇（引 CUI-0003），唔係疏忽。
- 明文寫真正擋住 alias flood 嘅係 `MAX_QUERY_TOKENS`：alias flood 係**闊**唔係**深**
  （重複 depth-2 field 幾百次），depth limiter 無論設幾多都攔唔到。
  票上第 1 點指出「AU-001 講嘅 depth limit 對今日攻擊面提供零保護」—— 呢句直接寫入 docstring。
- 指返兩條新測試做 gate。

### `tests/test_api.py`：兩條新測試（票上建議 1）

1. `test_the_depth_limiter_refuses_one_level_below_the_deepest_document`
   —— `build_schema(max_depth=4)` + `DEEPEST_CLIENT_QUERY` → **served**（斷言 `data["year"]` 有嘢，
   即真係行過 resolver，唔只係「validation 冇報錯」）；
   `build_schema(max_depth=3)` + 同一條 → **rejected**，訊息含 "depth"。
   呢個正正係票上「重現步驟」量到嘅 `max_depth=3: d4=REJECT` / `max_depth=4: d4=pass` 邊界。
   現有 `max_depth=2` 嗰條（`tests/test_api.py:416`）保留唔動，佢只證明 limiter 存在，
   呢兩條先證明 limiter **接上咗**。

2. `test_the_type_graph_stays_one_level_below_the_depth_limit`
   —— 由 `schema.as_str()` 嘅 SDL 起一個 `GraphQLSchema`，行匀成個 type graph 搵最深嘅 chain，
   斷言等於 4，同埋 `4 < MAX_QUERY_DEPTH`。
   **呢條先係票上「風險」嗰段嘅答案**：日後有人加深一層 nested field，呢條會紅，
   失敗訊息叫佢返去讀 `MAX_QUERY_DEPTH` docstring。測試 docstring 亦寫明呢個就係佢存在嘅理由。
   走 SDL 而唔係 `schema._schema`，係為咗唔掂 Strawberry private attribute，
   順帶令佢同 `run365-schema` export 嘅嘢對齊。
   `_deepest_selection` 帶住 `seen` path set —— graph 今日 acyclic，
   呢個係為咗佢唔再 acyclic 嗰日個 walk 仍然收斂。

**量度確認**：`_deepest_selection` 數埋 leaf 一層（回 5），`QueryDepthLimiter` 唔數 leaf（要 4），
所以測試入面減 1，呢點喺 helper docstring 寫明，避免下手誤讀。

**TDD 紀錄**：🔴 先將 `DEEPEST_REACHABLE_DEPTH` 設成 5（即「limiter 貼身」嘅假設）跑一次，
兩條測試都係 **AssertionError（Fail，唔係 collection Error）**——
`assert 4 == 5` 同埋 `max_depth=4` 冇拒絕；🟢 改返 4 轉綠。
