## 根本問題

一個描述 CI 行為嘅段落，同 `pages.yml` 之間**冇任何機制保證同步**。每次改 workflow 都要有人記得手動更新，而呢個 session 已經證明咗「記得」係唔可靠嘅 —— 兩次都係靠 reviewer / 下一個 lane 發現。

同樣風險亦適用於 `README.md` 同 `docs/deployment.md` 入面描述 CI 行為嘅段落。

## 建議方向

三選一（或組合）：

1. **由 `pages.yml` 生成** —— 寫個細 script 讀 workflow YAML，產出一段 markdown（觸發 branch、各 job 嘅 gate、部署來源），插入 docs 之間嘅 marker comment。CI 加一步檢查生成結果同 committed 版本一致（同 `run365-schema --check frontend/schema.graphql` 呢個現有 gate 同一個 pattern —— 該 gate 就係本 repo 已經證明有效嘅做法）。
2. **CI 加 drift 檢查** —— 唔生成，只斷言 docs 入面提到嘅 branch 名同 `pages.yml` 實際觸發清單一致。輕量好多，但只捉到 branch 名唔捉到語意。
3. **收窄描述** —— docs 唔再重複 workflow 細節，只指向 `pages.yml`。最平，但 docs 嘅可讀性會差。

⚠️ 留意 `docs/deployment.md` 新加嗰段切換 checklist（W-011 加）**特登列出四個地方六件事**，其中兩件喺 repo 外面（GitHub environment、Vercel dashboard）—— 呢啲**生成唔到**，任何自動化方案都要保留人手部分。

## 解決方案（2026-09-16，採用方案 3：收窄描述）

### 揀方案 3 嘅理由

- 方案 1（由 `pages.yml` 生成 markdown + CI gate）係另一個量級嘅工作：要寫 YAML reader、
  marker 插入器、CI 一步 drift 檢查，仲要維護生成器本身。用嚟解一段三行 prose 嘅 drift
  並唔划算，而且生成器本身亦係一個會腐爛嘅 artifact。如果日後真係要做，應另開票。
- 方案 2（CI 斷言 docs 提到嘅 branch 名同 workflow 一致）只捉 branch 名，捉唔到語意。
  今次第二次過時嘅正正係語意（「builds and deploys ... on pushes only」冇講明只限 `develop`），
  方案 2 捉唔到。
- 方案 3 由根源消除問題：docs 唔再持有一份會 drift 嘅 copy，就冇嘢可以 drift。
  唯一代價係讀者想知確切 job / step 要開 `pages.yml`，而 docs 已經明確指路。

### 實際改動

1. `docs/architecture.md` — CI bullet 唔再出現任何 branch 名、job 名或 step，改為講
   「CI 行上面嗰批 ruff / pytest gate 加前端檢查；static dashboard 由 workflow 指定嘅
   單一 deploy branch 部署」，並聲明 `pages.yml` 係 branch 清單同 job step 嘅 SSoT。
   （原文寫「every push and pull request to `master` ... deploys on pushes only」，兩項都錯。）
2. `README.md` — 「Continuous integration and deployment」段落刪走四個 job 嘅逐步
   清單（同 `deployment.md` 重複咗一次），改為高層描述 + 指向 `pages.yml`。保留
   「只有 `develop` 部署」一句，因為 `deployment.md` 嘅切換 checklist 第 4 項明文
   要求 README 呢一段喺換 deploy branch 時同步更新——呢個係有人手 procedure 覆蓋嘅
   受控引用，唔屬「靜靜過時」嗰類。
3. `README.md` —「Versioning and branches」段落原本寫 `master`「runs the same lint and
   test jobs **on its pull requests**」，實際 push 同 PR 都行，收窄成「is gated by the
   same CI checks」。
4. `docs/deployment.md` — 「GitHub Pages」section 刪走「The workflow has four jobs」
   嘅 job 數目、雙 branch 清單同四個 job 嘅指令逐項列表，保留形狀（乜嘢喺所有 gated
   branch 行、部署限一個 branch、`workflow_dispatch` 同一規則、404.html deep-link 行為）。
5. **切換 checklist 原樣保留**（四個地方六件事，其中 GitHub environment 同 Vercel
   dashboard 喺 repo 外，生成唔到亦唔可以刪）。改完之後亦核對過 checklist 第 4 項
   同最尾一句所指嘅位置全部仍然存在且仍然需要人手更新，冇令 checklist 本身失效。

## 驗證方式

⚠️ 原本寫嘅「改一次 `pages.yml` 嘅觸發 branch，確認 CI 會因為 docs 未同步而 fail」
**只適用於方案 1**：嗰條驗證方式假設咗存在一個由 workflow 生成 / 比對 docs 嘅 CI gate。
方案 3 之下根本冇引入任何 gate，改 `pages.yml` 嘅 branch 清單亦**應該**唔會令 CI 紅
（docs 已經唔再重複 branch 清單，所以本來就冇嘢要同步）。照跑只會得出一個必然綠嘅
結果，證明唔到任何嘢。

方案 3 對應嘅驗證方式：

1. **逐句核對**：改完之後，docs 剩低嘅每一句 CI / 部署描述都逐句對返
   `.github/workflows/pages.yml` 確認為真（見下面「已核實事實」）。
2. **drift 面積檢查**：確認 docs 已經冇任何 job 數目、job 名、step 指令、觸發 branch
   清單——即係改 workflow 嘅呢啲部分唔會再令任何一句 docs 變假。
3. **殘留 branch 名受控**：剩低提及 `develop` 嘅位置（README badge / CI 段 / 版本表、
   `deployment.md` intro / trigger 表 / Pages section / environment 規則）全部已經喺
   `deployment.md` 嘅切換 checklist 第 4 項同最尾一句列明，屬人手 procedure 覆蓋範圍。
4. **363 條現有測試全綠** + `ruff check src tests` + `ruff format --check src tests`
   全過，證明冇意外掂到代碼（本票零代碼改動）。

### 已核實事實（由 `.github/workflows/pages.yml` 讀出，非由 `CLAUDE.md` 抄）

- `on.push.branches` / `on.pull_request.branches` 都係 `[develop, master]`，另有 `workflow_dispatch`
- 四個 job：`lint-test`、`frontend`、`build`、`deploy`
- `lint-test`：`pip install -e ".[dev]"`、`ruff check`、`ruff format --check`、`pytest tests -q`、
  `run365-schema --check frontend/schema.graphql`
- `frontend`：`npm ci`、`npm run lint`、`npm run typecheck`、`npx vitest run`、api 同 static 兩個 build
- `build` 同 `deploy` 都 gated 喺 `if: github.ref == 'refs/heads/develop'`；`build` 會
  `cp dist/index.html dist/404.html`；`deploy` 行 `github-pages` environment
