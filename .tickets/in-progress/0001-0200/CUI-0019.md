## 問題描述

`src/api/service._sample_filter()` 為 batch 入面每條 track 砌一條 OR arm：

    or_(and_(activity_id == X1, position.in_([...])),
        and_(activity_id == X2, position.in_([...])), ...,
        activity_id.in_(whole))

SQLite 要對 `row_number() OVER (PARTITION BY activity_id ORDER BY seq)` subquery
嘅**每一 row** 評估呢 N 條 arm（EXPLAIN 顯示 `SCAN (subquery-3)` → `SCAN anon_1`），
所以總成本 ∝ batch 闊度 × batch 總 row 數 = **O(N²)**。
AU-050 之前每條 track 各自一句 index-bounded statement，成本係線性。

## 解決方案

**揀咗方向 1 嘅一個變體，冇行方向 2。**

方向 2（只 batch COUNT、SELECT 保留 per-track）會令 statement 數由 2 變返 N+1，
即係取消 AU-050 去解決 AU-050 引入嘅問題，亦會令
`test_a_page_of_tracks_costs_the_same_statements_however_wide_it_is` 變紅。
量度顯示唔需要做呢個取捨：predicate 本身可以做到固定大小，statement 數維持 2。

方向 1 票上寫嘅 `VALUES` / CTE 做法會令 bound parameter 由 `N x points + 2N`
變成 `2 x N x points`（**翻倍**），而 `test_the_widest_batch_stays_under_sqlites_bound_parameter_ceiling`
正正守住 `SQLITE_MAX_VARIABLE_NUMBER`。所以改為將 `(activity_id, position)`
**編碼成單一值**再用一條 `IN`，參數唔單止冇翻倍，仲少咗（見下）。

### 實際改動（`src/api/service.py`）

`_sample_filter()` 由：

    or_(and_(activity_id == X1, position.in_([...])), ..., activity_id.in_(whole))   # N+1 條 arm

改成：

    or_(sample_key.in_(["<position>:<activity_id>", ...]), activity_id.in_(whole))   # 最多 2 條 arm

其中 `sample_key` = `CAST(position AS VARCHAR) || ':' || activity_id`（新 `_sample_key()`）。

**點解個 key 係 injective**：position 係一串十進制數字，所以佢**唔可能含 `:`**。
position 行先，key 入面**第一個** `:` 就一定係分隔符；id 行先，**最後一個** `:` 就一定係分隔符。
兩種排法都唯一還原得返，**即使 activity id 本身含 `:`、係空字串、有前導零都一樣**。
而且呢度根本冇任何地方 parse 返個 key ——`IN` 淨係做 exact equality —— 所以真正需要嘅性質只係 injectivity。

**position 行先係任意選擇**，純粹因為讀落順，唔係因為佢先 injective。

> **更正（W-026，2026-09-16）**：呢段原文寫「如果 id 行先就冇呢個保證……**次序先係承重嗰半**」——
> **呢個論證係假嘅**（結論「key injective」本身啱，錯嘅係理由）。
> Brute-force 實測：14 個含 `:` / 空 / 前導零 / 非 ASCII 嘅 id × 132 個 position，
> position-first 同 id-first **兩種排法各 0 collision**。
> 真正承重嘅唔係次序，而係「**其中一半嘅 rendering 保證唔含分隔符**」——
> 呢度係 position。如果 position 嘅 rendering 有朝含到分隔符，**兩種排法會一齊爆**，
> 而且係靜靜雞 match 唔到而唔係報錯。
>
> 同一個錯講法亦寫咗喺 `f57caa8` 嘅 commit message 第 3 段。
> 嗰個 commit 已經 merge 咗入 `claude/ai-dev-team-start-05jie2` 兼 push 咗，
> **改唔到**，所以喺度留低更正紀錄；`SAMPLE_KEY_SEPARATOR` 嘅 docstring 亦已經改寫。

> **更正（W-025，2026-09-16）**：上面呢段原文寫「`cast()` 唔係裝飾：`position` 係 integer
> column，SQLAlchemy 對 integer 嘅 `concat` 會 render 成算術加法而唔係 `||`」——**兩個分句都係假**，
> 已實測證偽（SQLAlchemy 2.0.54）：
>
> - `numbered.c.position.type` 係 `NullType()`，唔係 `Integer()`；佢係 `row_number() OVER (...) - 1`
>   嘅 label，SQLAlchemy 解唔到 type。
> - 真正嘅 Integer mapped column 做 `.concat()` 一樣 render `||`
>   （`TrackPoint.seq.concat(":")` → `track_points.seq || ?`）。render 成加法嘅係 `+`，唔係 `concat`。
>
> `cast()` **保留**，但理由係：佢令 expression 嘅 type 由 `NullType` 變 `String`，
> 令「呢度做緊 text concatenation」寫喺 SQL 同 SQLAlchemy type 上，而唔係淨靠 SQLite `||` 嘅隱式
> coercion。拎走 cast 之後值唔變（408 個值實測 `||`、`CAST(... AS VARCHAR) ||` 同 Python `str()` 全等）、
> 365 條測試照樣全綠，所以係 explicitness 而唔係 necessity。
> 真正承重嘅 invariant 係 Python 同 SQLite 對 position 嘅字串化必須一致，
> 所以 `_even_positions()` 一定要繼續回 `int`。詳見 `_sample_key()` docstring。

### 成本

SQLite 對「一條 `IN` + 一串 constant」會起一個 ephemeral index，每 row 一次 lookup，
所以成本 ∝ batch 掃嘅 row 數，同 batch 闊度無關。`EXPLAIN QUERY PLAN` 結構不變
（`SCAN (subquery-3)` → `SCAN anon_1`），改變嘅係每 row 要做幾多功。

### Bound parameter

`batch_parameters()` 由 `a*p + 2a + 1` 變 `a*p + a + 2`：每條 track 唔再第二次 bind 自己個 id
（`==` arm 冇咗，id 而家喺 key string 入面），多咗一個分隔符參數。

| shape | 修復前 | 修復後 |
|---|---|---|
| 50 x 200（使晒 points budget） | 10,101 | **10,052** ← 而家係最大值 |
| 64 x 156（使晒 field cap） | 10,113 ← 舊最大值 | 10,050 |

per-track 項由 2 跌到 1，令 W-020 搵到嘅 crossover **倒返轉**：最大值返去 50 x 200。
兩個 shape 都仍然有 test 行過；constant 改名成 `POINTS_BUDGET_BATCH_*` /
`FIELD_CAP_BATCH_*`，**按形狀命名而唔係按排名**，因為呢個排名已經反轉過兩次。
`worst * 3 < SQLITE_BOUND_PARAMETER_CEILING` 嘅餘裕斷言保留（10,052 x 3 = 30,156 < 32,766）。
