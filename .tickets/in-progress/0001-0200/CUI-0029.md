## 問題描述

`_charge_list_rows` 同 `_charge_track_field` 用 `raise ValueError(...)` / `raise RuntimeError(...)`
表達「呢個 request 超咗 budget」。Strawberry 將任何由 resolver 掟出、而唔係
`GraphQLError` 子類嘅 exception 當成**未預期錯誤**，經 `strawberry.execution` logger
以 `ERROR` level 連同 `exc_info` 記落去。

即係話：**一個完全喺預期之內、由設計明確要求發生嘅拒絕，被當成 server 出事咁記錄。**

## 影響

**回俾 client 嗰面係乾淨嘅**（QA 已核實，唔使改）：response 只有一句
`"list row budget exhausted: one request may read at most 4000 rows"`，
冇 context key 名、冇 traceback、冇路徑。問題純粹喺 server log 嗰面。

1. **資訊洩漏（低強度）**：部署 log 寫低絕對檔案路徑、目錄佈局同 Python / 套件版本路徑。
   Vercel function log 由 dashboard 睇得到。
2. **Log 量放大（呢個先係實際成本）**：觸發成本係 **998 token 一個 request、public
   read-only endpoint、唔使認證**（CUI-0027 票上量過）。即係話任何人可以用極低成本
   令 log 每秒堆幾十個 10-frame traceback。呢個係 CUI-0027 特登要擋嘅嗰種放大，
   只不過搬咗去 log 嗰一層。
3. **Signal 溝淡**：`ERROR` + traceback 本來應該代表「要人去睇」。而家最常見嘅 `ERROR`
   會係一個**設計上正常**嘅拒絕，真正嘅 500 反而埋沒喺入面。

## 實測修正（2026-09-16，Backend Developer）

張票推薦嘅**方案 A 原樣係唔 work 嘅**，實測結果如下。

`strawberry.utils.logging.StrawberryLogger.error` 行嘅係
`logger.error(error, exc_info=error.original_error)` —— 即係「有冇 traceback」完全取決於
`original_error` 呢個 attribute 有冇被 set，同 exception 係咩 type **冇直接關係**。

而 `graphql.error.located_error` 只喺**掟出嚟嗰個 error 本身已經有 `path`** 嘅時候先會原樣放行：

```python
if isinstance(original_error, GraphQLError) and original_error.path is not None:
    return original_error
```

一個喺 resolver 新 `raise` 出嚟嘅 `GraphQLError` 係**冇 `path`** 嘅，所以照舊被包一層、
`original_error` 照樣被 set、traceback 照樣出。實測：單純換成 `GraphQLError`（或者佢嘅 subclass）
之後，`exc_info` 仍然係 `True`，9 個 frame 一個都冇少。

**真正生效嘅做法**：掟一個**帶住 resolver 自己 `path` 同 `field_nodes`** 嘅 `GraphQLError`
（見 `BudgetExceededError`）。咁 `located_error` 就原樣放行，`original_error` 係 `None`，
`exc_info` 變 `False`。`nodes` 唔可以慳 —— 慳咗 client 就冇咗 `locations`。

| 量度 | 修正前 | 修正後 |
|---|---|---|
| `Traceback` 數（無 logging 設定） | 1 | **0** |
| 帶絕對路徑嘅 frame | 9 | **0** |
| client `errors[0]` keys | `locations` / `message` / `path` | **一模一樣** |
| client `errors[0].message` | — | **逐字不變** |
| 未 seed 嘅 `RuntimeError` | 有 traceback | **仍然有 traceback** |

三個 mutant 全部被殺（去 `path=` / 去 `nodes=` / 淨 `GraphQLError`），
第三個就係張票原本嘅方案 A。

### Log level（2026-09-16，用戶拍板順手做埋，唔另開票）

用戶決定：override `strawberry.Schema.process_errors`，將例行拒絕降到 `ERROR` 以下。

#### 揀咗 `INFO`（唔係 `WARNING`）

兩個理由，一個講意思、一個實測：

1. **意思**：拒絕唔係降級狀態、亦唔係差啲出事。Request 問多過契約俾嘅，契約講咗「唔得」，
   client 收到一句佢處理得到嘅訊息。Server 冇嘢要人跟進，就唔應該去到一個叫人跟進嘅 level。
2. **實測**：`logging` 嘅預設 threshold 係 `WARNING`。一個**乜都冇設定**嘅部署
   （即 Vercel 預設，亦即本票量度嗰個條件）會**完全 drop 咗呢啲 record**，
   所以影響 2（log 量放大，998 token 一個 request、免認證）由「一行 per request」變成 **0**。
   揀 `WARNING` 嘅話，預設之下每個被拒 request 仍然寫一行。
   想睇拒絕（調 budget、或者捉緊有人狂 hammer）嘅 operator 自己調低 level 就全部見到。

冇犧牲嘅嘢：拒絕仍然入**同一個 logger**（`strawberry.execution`）、**同一句 message**，
係預設之下靜咗，唔係喺源頭掉咗。

#### 點確保真 error 仍然 `ERROR` + traceback

`RefusalAwareSchema.process_errors` 只認 **`BudgetExceededError` 呢個 type**，
其餘全部原封不動交返俾 `super()`：validation error、`Int` coercion failure、
未 seed budget 嘅 `RuntimeError`、resolver 爆錯 —— 全部保留 `ERROR` 同 `exc_info`。

用 **type 唔用 message 字串**（即張票方案 B 嘅弱點）：靠字眼匹配嘅 filter 會喺
一個真 fault 啱啱提到 "budget" 嗰陣靜咗佢，亦會喺措辭一改嗰日停止生效。

⚠️ `process_errors` 見到嘅係**成個 operation 所有 error**，唔淨止 budget，
所以「認一種、順手掃埋其餘」係一個 budget 測試完全睇唔到嘅一行錯。

  原本嗰條 unseeded 測試用緊 plain `strawberry.Schema`，即係**根本冇行過**本 fix 嘅 class，

  係因為要釘住嘅係「同 production 同一個 class」，唔係嗰個 identifier。
