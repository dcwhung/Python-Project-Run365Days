## 問題描述

`MAX_TRACK_FIELDS_PER_REQUEST`（64 個 `track` field）同 `MAX_TRACK_POINTS_PER_REQUEST`（10,000 點）
只綁住 **track** 嗰半。**list field 嘅 fan-out 冇任何 budget 綁住** —— `src/api/schema.py:173`
自己白紙黑字寫住「no budget here bounds it」。

即係話一個**完全唔攞 track** 嘅 document，只要 alias 夠多個 `activities`，
就可以行得比任何合法 track shape 慢一個數量級。

## 實測（兩個獨立量度，互相印證）

| 量度者 | 166 個 aliased `activities`（零 track）|
|---|---|
| Backend Developer | **3,228 ms** |
| Code Reviewer（獨立重寫 script） | **3,072 ms** |

對照（同一個 production export，365 activities / 134,041 track rows）：

| Document shape | 時間 |
|---|---|
| **166 aliased `activities`（零 track）** | **~3,100 ms** |
| 最差合法 track shape（`limit:64 points:156`） | 272.5 ms |
| `limit:64 points:1`（CUI-0019 之後） | 58.2 ms |

**領先第二名 11 倍**，而且係喺 CUI-0019 令 track 路徑快咗之後 —— 即係 track 嗰半已經修好，
呢個反而變成咗最慢嗰條路。

## 影響範圍

- **餘裕**：15 s Vercel function 之內只得 **~4.9×**。所有 track shape 而家都有 **50×** 以上
- **Vercel CPU 慢過開發機 2–3×** ⇒ 實際 6–9 s，距離 hard limit 唔夠 2×，**仲未計 cold start**
- **零成本可觸發**：998 token（喺 `MAX_QUERY_TOKENS = 1000` 之內）、public read-only endpoint、唔使認證
- **今日前端零影響**：冇任何 document 咁樣寫

## 點解係 🟠 High 而唔係 🔴 Critical

`MAX_QUERY_TOKENS = 1000` 令 166 已經係 alias 數上限 —— 即係話呢個係一個**有上界但上界太鬆**
嘅成本，唔係 unbounded。所以唔係即時 outage 風險，但係現時所有已知合法 document 入面最差嘅一個，
而且係唯一一個餘裕喺個位數嘅。

## 建議修復方向（由 developer 判斷）

1. **為 list fan-out 設 request 層 budget**，按**回傳 row 數**收費（唔係按 field 數）——
   同 `MAX_TRACK_POINTS_PER_REQUEST` 同一個 pattern，令一個 request 讀幾多行有個明確上限
2. **或者將 `SQL_PER_LIST_FIELD` 亦 batch** —— 166 × 2 = 332 條 statement 變 2 條，
   同 AU-050 對 track 做嘅嘢一樣。⚠️ 但要留意 CUI-0019 嘅教訓：AU-050 將 statement 數壓平之後
   引入咗一個 O(N²) predicate，**statement 數唔等於成本**。呢條路要有 CUI-0019 同款嘅
   「成本隨闊度線性」測試接住
3. 兩條路都要：**非 wall-clock 嘅回歸 gate**（CUI-0019 用咗 arm-count + VDBE-step，可參考），
   同埋**量度必須用 production 規模**（600-row fixture 睇唔到，見 CUI-0020）
