## 問題描述

`MAX_TRACK_FIELDS_PER_REQUEST`（64 個 `track` field）同 `MAX_TRACK_POINTS_PER_REQUEST`（10,000 點）
只綁住 **track** 嗰半。**list field 嘅 fan-out 冇任何 budget 綁住** —— `src/api/schema.py:173`
自己白紙黑字寫住「no budget here bounds it」。

即係話一個**完全唔攞 track** 嘅 document，只要 alias 夠多個 `activities`，
就可以行得比任何合法 track shape 慢一個數量級。

## 實測（兩個獨立量度，互相印證）

| 量度者 | 166 個 aliased `activities`（零 track）|
|---|---|
| Backend Developer | **3,228 ms** |
| Code Reviewer（獨立重寫 script） | **3,072 ms** |

對照（同一個 production export，365 activities / 134,041 track rows）：

| Document shape | 時間 |
|---|---|
| **166 aliased `activities`（零 track）** | **~3,100 ms** |
| 最差合法 track shape（`limit:64 points:156`） | 272.5 ms |
| `limit:64 points:1`（CUI-0019 之後） | 58.2 ms |

**領先第二名 11 倍**，而且係喺 CUI-0019 令 track 路徑快咗之後 —— 即係 track 嗰半已經修好，
呢個反而變成咗最慢嗰條路。

## 影響範圍

- **餘裕**：15 s Vercel function 之內只得 **~4.9×**。所有 track shape 而家都有 **50×** 以上
- **Vercel CPU 慢過開發機 2–3×** ⇒ 實際 6–9 s，距離 hard limit 唔夠 2×，**仲未計 cold start**
- **零成本可觸發**：998 token（喺 `MAX_QUERY_TOKENS = 1000` 之內）、public read-only endpoint、唔使認證
- **今日前端零影響**：冇任何 document 咁樣寫

## 點解係 🟠 High 而唔係 🔴 Critical

`MAX_QUERY_TOKENS = 1000` 令 166 已經係 alias 數上限 —— 即係話呢個係一個**有上界但上界太鬆**
嘅成本，唔係 unbounded。所以唔係即時 outage 風險，但係現時所有已知合法 document 入面最差嘅一個，
而且係唯一一個餘裕喺個位數嘅。

## 建議修復方向（由 developer 判斷）

1. **為 list fan-out 設 request 層 budget**，按**回傳 row 數**收費（唔係按 field 數）——
   同 `MAX_TRACK_POINTS_PER_REQUEST` 同一個 pattern，令一個 request 讀幾多行有個明確上限
2. **或者將 `SQL_PER_LIST_FIELD` 亦 batch** —— 166 × 2 = 332 條 statement 變 2 條，
   同 AU-050 對 track 做嘅嘢一樣。⚠️ 但要留意 CUI-0019 嘅教訓：AU-050 將 statement 數壓平之後
   引入咗一個 O(N²) predicate，**statement 數唔等於成本**。呢條路要有 CUI-0019 同款嘅
   「成本隨闊度線性」測試接住
3. 兩條路都要：**非 wall-clock 嘅回歸 gate**（CUI-0019 用咗 arm-count + VDBE-step，可參考），
   同埋**量度必須用 production 規模**（600-row fixture 睇唔到，見 CUI-0020）

## 執行紀錄（2026-09-16）

**方案**：票上方向 1（按 row 數收費嘅 request 層 budget），**冇**行方向 2（batch `SQL_PER_LIST_FIELD`）。

點解唔行方向 2 —— 由量度決定，唔係偏好：166 個 field 發 332 條 statement 共 ~2,900 ms，
但**每條 statement 只係 ~9 ms**。真正成本係 60,590 行 ORM materialisation + GraphQL resolution，
按行線性。Batch 成兩條 statement 一樣要 materialise 同樣多行，慳唔到主成本，
卻要重新引入 AU-050 嗰種 wide predicate 風險（就係 CUI-0019 啱啱修好嗰個）。

### 用戶決定（2026-09-16，三項）

| 決定 | 值 | 理據 |
|---|---|---|
| `MAX_LIST_ROWS_PER_REQUEST` | **4000** | 前端實際最大需求嘅 8×；四個 list field 全部用 `MAX_PAGE_SIZE = 1000` 一次過拎啱啱好 4000，即「文件寫明嘅最大 page size × 全部 list field」仍然合法；由成本反推最貴一行 0.13 ms × 4000 ≈ 520 ms |
| Breaking change | **接受** | 「同一 request 內所有 list field 嘅 `limit` 加起身 > 4000」會被拒。前端五個 document 今日全部 served（各有 test pin 住），但呢個係 public endpoint，第三方影響未知 |
| Alias 軸 | **記錄但不處理，不開票** | 見下 |

### ⚠️ DoD「餘裕 ≥ 20×」嘅豁免（要留痕）

本票 DoD 寫「15 s function 之內嘅餘裕同 track shape 同一個數量級（目標 ≥ 20×）」。

**實測最差合法 document 係 18.2×，未達 20×** —— 但差額**唔係** list fan-out 造成：

- List fan-out 本身已修好：166 aliased `activities` 由 ~2,900 ms → 161 ms；最差「仍然 served」
  嘅 list shape 係 477 ms = **31.4×**，達標
- 而家最慢嘅係**另一條軸**：`{ activities { x0: warnings … x330: warnings } }`
  （一頁、charge 500、331 個 aliased leaf），reviewer 獨立量到 **824 ms = 18.2×**。
  呢條軸嘅成本隨「resolve 咗幾多個 field」而唔係「讀咗幾多行」增長，
  **row budget 原理上綁唔到**（實測：budget 收到 500，呢個 shape 仍然 881 ms）

用戶決定**記錄但不處理、不開新票**。記錄載體係 `MAX_LIST_ROWS_PER_REQUEST` 個 docstring
（已寫低嗰條軸、佢嘅數字、同埋 row budget 綁唔到佢嘅原因）。
所以本票係**喺一個明文豁免之下結案**，唔係 DoD 全數達成。日後有人要收拾嗰條軸，
可能嘅方向係 Strawberry `MaxAliasesLimiter` 或者 per-request resolved-field budget ——
兩者都係另一個常數 + breaking change 決定。

### 額外發現（票上冇提）

`166 個 aliased year` 喺修復前係 **~2,800–3,400 ms，比票上嗰條仲慢** ——
`year` 每次都 unwindowed 讀成年 + 全部 aggregate，之前一樣冇 budget。修復後被拒。
