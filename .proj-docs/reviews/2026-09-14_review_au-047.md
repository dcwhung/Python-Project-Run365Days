## 🔴 C-001 — budget 扣 points 唔扣 round trip，15 秒 envelope 依然守唔住

**位置**：`src/api/schema.py:43-56`（`MAX_TRACK_POINTS_PER_REQUEST` 及其 docstring）、`:155-162`（`_charge_track_points`）

### 問題

1. `_charge_track_points` 每個 `track` field 扣 `points`，唔理呢個 field 要行幾多次 SQL。
2. 每個 `track` field **一定**係一次獨立 round trip（`service.track()`，AU-050 之前無 batching），今日係 1 COUNT + 1 SELECT。
3. 所以 `points=1` 嘅 track field **用最平嘅 budget 成本（1 點）換最貴嘅系統成本（2 條 SQL）**。
4. `activities(limit: 365)` 一個 field 可以一次 fan out 365 個 `track` field，即 365 點換 730 條 SQL。
5. 用 alias 複製：27 × 365 = **9,855 點**，喺 10,000 budget 之內；`QueryDepthLimiter(5)`（depth 只有 3）同 `MaxTokensLimiter(1000)` 都過。

### 實測（365 activities × 600 stored points 嘅 production-shaped DB，真 Flask test client）

```
== K. accepted alias flood, 3 repeats (budget = shipped 10000) ==
   27 aliases, 9855 pts charged (run 1)           sql= 19764  13.14s errors=0
   27 aliases, 9855 pts charged (run 2)           sql= 19764  14.13s errors=0
   27 aliases, 9855 pts charged (run 3)           sql= 19764  14.09s errors=0

== L. same shape with the budget effectively off (pre-AU-047 behaviour) ==
   52 aliases, budget disabled                    sql= 38064  27.14s errors=0

== M. the shape AU-047 measured, before/after ==
   activities(365){track(1000)} budget off        sql=   732   3.71s errors=0
   activities(365){track(1000)} budget on         sql=    22   0.12s errors=1

== C. how much work a REJECTED alias flood still does ==
   30 aliases x activities(365){track(1)}         sql= 20056  13.04s errors=1
   52 aliases x activities(365){track(1)}         sql= 20056  14.24s errors=1

== J. what the same attack costs at a lower budget ==
   budget= 10000: sql= 20056  14.07s errors=1
   budget=  3000: sql=  6018   4.24s errors=1
   budget=  1000: sql=  2006   1.44s errors=1
```

**算術核實（main agent 獨立對數）**：27 × 365 = 9,855 個 track field × 2 條 SQL = 19,710，加 27 個 alias 各自 2 條（activities + warnings selectinload）= **19,764**，同實測完全一致。另用我哋自己量到嘅 ~0.8 ms／query 推算：19,764 × 0.8 ms ≈ **15.8 s**，同 reviewer 量到嘅 13–14 s 同一量級。

### 點解係 Critical

- Reviewer 部機行 AU-047 原本條 benchmark 係 **3.71 s**，我哋量到 **8.29 s** —— 真機慢約 2.2×。同比推算，呢條 alias flood 喺 Vercel 上約 **30 秒**，撞爆 15 s function limit（504），而且係一條**未認證嘅公開 POST**。
- 被拒嘅請求一樣燒晒時間（20,056 SQL / 13 s）：budget 使爆之前發出嘅 query 錢照付，GraphQL 亦唔會喺第一個 error 就收工。
- docstring 兩句結論被實測否證：「10,000 rows costs about 0.37 s」同「The cost is building the rows, not the per-activity round trips, so batching the queries would not have bought the headroom back」。後者正正係 AU-050 唔做 batching 嘅理由。

### 採用方案（2026-09-14 用戶拍板）

**方案 A —— 加獨立嘅 round-trip / field counter**：`MAX_TRACK_FIELDS_PER_REQUEST = 64`，同 points budget 正交。

64 嘅理據：points budget 喺 default `points=150` 之下**已經隱含**咗 `10000 // 150 = 66` 個 field 嘅上限，攻擊就係靠將 `points` 壓到 1 去繞過佢。所以顯式定 64 對現有合法用法接近零影響，但徹底封死放大。最壞 64 × 2 = 128 條 SQL。AU-050 做完 batching 之後可以獨立放寬。

（未採用：方案 B `cost = max(points, K)` 一條公式收兩樣嘢，SDL 難解釋；方案 C 淨係調低 budget —— 攻擊成本同 budget 成線性，只係將個洞縮細唔係封咗。）

## 🟡 W-012 — `10000` 嘅理據引用咗一份 dashboard 根本發唔出嘅 document

**位置**：`src/api/schema.py:53-56`；對照 `frontend/src/data/api/queries.ts:9-33`、`:128-144`、`frontend/src/views/activity/ActivityView.tsx:17`

docstring 話「10,000 is twice the most expensive document the dashboard can send: the five activities of `YearQuery`'s `personalBests` … comes to 5,000」。

但 `personalBests` 五個 field 全部只 spread `...ActivityFields`，而 **`ActivityFields` fragment 由頭到尾冇 `track`** —— `YearQuery` 嘅 track budget 消耗係 **0**。前端唯一攞 track 嘅係 `TrackQuery`，單一 activity，`ActivityView.tsx:17` 寫死 `TRACK_POINTS = 600`（`source.ts:20` default 都係 600，唔係 1000）。

真實 client 上限係 **600 點**，唔係 5,000。10,000 唔係「兩倍 headroom」，係 **16.7 倍** —— 而呢個過大嘅數字就係 C-001 攻擊嘅本錢。

**決定**：budget 維持 10000（有咗 field cap 之後 rows 已唔係主要風險），但理據改寫成誠實版本 —— 一個 round-number ceiling，唔係由 client 需求推導。

## 🟡 W-013 — `isinstance(context, MutableMapping)` 守得住，但寫低嘅理由係錯

**位置**：`src/api/schema.py:119-131`（特別係 `:128-130` 註解）、`:149-153`（`Raises: KeyError`）

逐個 context 形狀實測（`schema.execute_sync(context_value=...)`）：

```
no context_value            rows=None  TypeError: 'NoneType' object is not subscriptable
dict                        rows=600   ok
MappingProxyType            rows=None  KeyError: 'track_points_remaining'
plain object                rows=None  TypeError: 'Ctx' object is not subscriptable
dict 預先塞 budget=5        rows=600   ok（extension 覆寫咗 caller 塞嘅值）
```

**冇任何路徑令 `track` 變返 unbounded**（developer 呢點啱），Strawberry batching 亦預設熄咗（`_validate_batch_request`：`batching_config is None` → HTTP 400），所以冇 batch 旁路。

**但個理由錯**：註解寫「冇 context mapping 就去唔到 `track`」—— `MappingProxyType`（任何 read-only `Mapping`）唔係 `MutableMapping`，guard 唔 seed，但 `info.context["session"]` 讀得到，`track` 係去到嘅。真正守住佢嘅係 `_charge_track_points` 嗰個 `KeyError`。連帶 `Raises:` 少講咗第二個成因，而 client 會收到一個赤裸嘅 internal key（`'track_points_remaining'`）。

## ✅ 做得好嘅地方

- **per-request 隔離係真嘅**，三個獨立證據：6 次連續 full-budget request 全部成功；4 次 request 造出 4 個唔同 extension instance id 且 instance 上無 budget state；同一個 context dict 重用三次每次都由 10000 重新 seed。State 喺 per-request context dict，唔喺 module-level `schema` singleton。
- **`test_the_budget_is_per_request_and_does_not_leak_across_requests` 唔係假綠 —— 經 mutation test 證實**。Reviewer 寫咗個 pytest plugin，runtime 將 `_charge_track_points` 換成 module-level 全局 counter 兼拆咗 seeding（**冇改過 repo 任何檔案**，`git status` 全程 clean），單獨跑嗰條測試即紅，全套再多 4 條紅。冇再出 `PYTHONTZPATH` 嗰種永遠綠。
- **邊界 off-by-one 釘得準**：`test_a_request_that_exactly_spends_the_budget_is_served` 令 `remaining` 啱啱好 0 都要放行 —— `< 0` 寫成 `<= 0` 即刻紅。
- **`ACTIVITIES_THAT_FIT = MAX_TRACK_POINTS_PER_REQUEST // MAX_TRACK_POINTS` 係推導，唔係 hardcode**，兩個常數點改都唔會 drift。
- **「扣 requested points 唔扣實際行數」嘅取捨喺 `_charge_track_points:136-140` 講得非常清楚**，連對誠實 client 嘅代價都寫明。方向正確：唔喺 SQL 出去之前拒絕就唔叫 bound。
- **budget 覆寫 caller 塞入 context 嘅值**，所以 context 唔會成為調高 budget 嘅旁路。
- **SDL description 內嵌常數值**（f-string 引 `MAX_TRACK_POINTS_PER_REQUEST`），常數改咗 `run365-schema --check` 就會喺 CI 叫 —— 跟足 S-012 定落嘅 pattern。
