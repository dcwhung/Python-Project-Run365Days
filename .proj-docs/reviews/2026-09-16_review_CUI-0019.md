## 一、獨立核實（唔照單全收）

### 1.1 Composite key 嘅正確性 —— 本次最高風險

#### (a) Injectivity 論據成唔成立？

**結論：key 係 injective ✅，但 developer 寫嘅理由係錯嘅 ❌（見 W-026）。**

我自己推一次：`key = str(position) + ":" + activity_id`。`str(position)` 對任何 Python `int`
都唔含 `":"`，所以 key 入面**第一個** `":"` 必然喺 index `len(str(position))`。
兩條 key 相等 ⟹ 第一個 `":"` 位置相同 ⟹ `str(p1) == str(p2)` ⟹ `p1 == p2`，再推出 `id1 == id2`。
**對任何 activity id 都成立**，包括含 `":"`、空字串、非 ASCII、前導零、負 position。✅

但 developer 話「id 行先就冇呢個保證」—— **呢句係錯嘅**。
`key = activity_id + ":" + str(position)` 一樣 injective：`str(position)` 唔含 `":"`，
所以 key 入面**最後一個** `":"` 必然係分隔符，同樣可以唯一還原。
真正承重嘅唔係次序，係「position 呢一邊嘅 rendering 唔含分隔符」。
Brute-force 驗證（14 個含 `":"` / 空 / 前導零嘅 id × 132 個 position）：

```
position-first: 1848 keys from 1848 rows, collisions=0
id-first:       1848 keys from 1848 rows, collisions=0
```

#### (b) 真實 export 嘅 activity id 形態

由重 build 嘅 production DB 直接讀：

```
365 activities; id charset: 0123456789 ; id lengths: [(10, 365)] ; ids containing ':': 0
```

全部係 10 位純十進制數字（Garmin activity id，由 `file_path.stem.rsplit("_", 1)[-1]` 得出，
見 `src/activities/parsers/{tcx,gpx,kml}.py:60`）。即係話**生產上點排都唔會撞**。

#### (c) `CAST(position AS VARCHAR)` 喺 SQLite 嘅行為

實測：

| 輸入 | SQLite `CAST(? AS VARCHAR)` | Python `str()` | 一致 |
|---|---|---|---|
| 0 / 1 / 9 / 10 | `'0' '1' '9' '10'` | 同 | ✅ |
| −1 | `'-1'` | `'-1'` | ✅ |
| 123456789012345 | `'123456789012345'` | 同 | ✅ |

無前導零、無正號、無科學記數。NULL 唔可能出現：`position` 係
`row_number() OVER (...) - 1`，window function 永遠唔回 NULL；`activity_id` 係 PK NOT NULL。
負數理論上唔會出現（`row_number()` 由 1 起），就算出現 key 一樣 injective。

#### (d) Python 側 vs SQL 側字串化一致

兩邊都係整數十進制 rendering，上表逐個對過，**完全一致 ✅**。
唯一會令兩邊分家嘅情況係 `_even_positions()` 改成回 float（`str(2.0)='2.0'` vs
`CAST(2.0 AS VARCHAR)='2.0'` 其實都一致，但 `position` 係整數就唔 match）——
而 `_even_positions()` 用 `round()`（Python 3 回 `int`），一旦變 float，
現有大量 sampled 內容斷言會即刻紅，所以呢個 invariant 有 gate 守住。

#### (e) 對抗性 fixture 實測

我另建一個 DB，activity id 專登揀到**如果 key 砌反就會撞**嘅形態
（`"1"`, `"1:2"`, `"2"`, `"a:1"`, `"a"`, `""`, `"0"`, `"007"`, `"駿"`, `"12:3"`, `"3:12"`, `"x"*40`），
track 長度 0/1/2/3/7/10/11/17/100/101/250/601，對 20 個 points 值
（含 `None`/0/1/2/149/150/151/599/600/601/1000）同一個**純 Python reference 實作**逐點比對：

```
adversarial ids: 480 comparisons, 0 mismatches
```

呢個 fixture 亦順帶覆蓋咗任務單提到嘅「冇 track 嘅 activity」（長度 0）同
「track 短過 points」（長度 1/2/3 配 points=10）——**production DB 冚唪唥冇呢兩種**
（min 250 / max 600 rows，零 trackless activity），所以呢個 fixture 係唯一覆蓋到嗰兩個 case 嘅地方。

### 1.3 Bound parameter 公式反轉 —— 核實正確

自己推一次新公式 `a*p + a + 2` 嘅四個項：

| 項 | 來源 | 數 |
|---|---|---|
| `a*p` | 每個 sample 一條 key，`_sample_key(...).in_(keys)` | a×p |
| `a` | `numbered` subquery 嘅 `activity_id.in_(wanted)` | a |
| `+1` | `row_number() OVER (...) - 1` 個 `- 1` | 1 |
| `+1` | `.concat(SAMPLE_KEY_SEPARATOR)` 嘅 `":"`，全條 statement 只 bind 一次 | 1 |

舊公式 `a*p + 2a + 1` 嘅第二個 `a` 係每條 track 喺自己 `== X` arm 再 bind 一次 id——
`==` arm 冇咗，所以 per-track 項由 2 跌到 1，多咗一個分隔符參數。**推導成立 ✅**。

我獨立 sweep 晒三個 budget 容許嘅全部 `(activities, points)`：

```
budgets: MAX_TRACK_POINTS_PER_REQUEST=10000  MAX_TRACK_FIELDS_PER_REQUEST=64  MAX_TRACK_POINTS=1000
max shape (50, 200) = 10052
64x156 = 10050   50x200 = 10052
3 x max = 30156 < 32766 : True
```

- 最壞值 **10,052** vs `SQLITE_MAX_VARIABLE_NUMBER = 32,766` → 餘裕 **3.26x** ✅
- crossover 確實倒返轉（10,113/10,101 → 10,050/10,052），最大值由 64×156 返去 50×200 ✅
- `test_the_widest_batch_stays_under_sqlites_bound_parameter_ceiling` 兩個 shape 都參數化行過，
  用嘅係**真實 statement 嘅 bound param 數**（`sql_params` fixture）而唔係公式自證，
  兩個 expected（10052 / 10050）綠 ✅
- 上界斷言由 `+ 2 * FIELDS` 改成 `+ FIELDS + 2` = 10,066 ≥ 10,052，仍然係 tight bound ✅

**改名合理 ✅**。`POINTS_BUDGET_BATCH_*` / `FIELD_CAP_BATCH_*` 按形狀而唔係按排名命名，
係直接回應 W-020 嘅根因（fixture 個名自稱係 worst case，排名一變個名就講大話）。
兩個 shape 都仍然有測試行過，排名由
`test_no_batch_the_budgets_allow_binds_more_parameters_than_the_maximum` 決定而唔係由 docstring 決定。
兩者只差 **2 個參數**，developer 自己喺 docstring 明寫「close enough that nothing should rest on
which side wins」——呢個係啱嘅態度。

另外核實：mixed batch 唔會爆過 all-sampled 上限。混合時每條 whole track 出 1 個參數
（`whole` arm），每條 sampled track 出 p 個 key；因為 `p >= 1`，
`a + Σ_sampled p + Σ_whole 1 + 2 <= a*p + a + 2`。`batch_parameters` docstring 講
「A track taken whole is cheaper than this」**成立 ✅**。

### 🟡 W-025 — `_sample_key()` docstring 為個 `cast()` 寫嘅理由係假嘅

**位置**：`src/api/service.py:216-218`

```python
The cast is not decoration: ``position`` is an integer column, and
SQLAlchemy renders ``concat`` on an integer as arithmetic addition rather
than as ``||``.
```

**描述**：呢句兩個分句都經實測證偽（SQLAlchemy 2.0.54 + SQLite dialect）：

1. **「`position` is an integer column」——唔係。**
   `numbered.c.position` 係 `row_number() OVER (...) - 1` 個 label，
   SQLAlchemy 解唔到佢嘅 type：

   ```
   numbered.c.position.type  →  NullType()
   ```

2. **「SQLAlchemy renders `concat` on an integer as arithmetic addition」——唔係。**
   對一個**真正嘅 Integer mapped column** 都一樣 render 成 `||`：

   ```
   models.TrackPoint.seq.concat(":").concat(...)
     →  track_points.seq || ':' || track_points.activity_id
   ```

   （`+` 先至會變加數。`concat()` 係 explicit 嘅 `concat_op`，SQLAlchemy 對佢一律出 `||`。
   估計係寫嗰陣試過 `+` 見到加數，事後歸因落 `concat` 度。）

3. **`cast` 拎走之後 365 條測試照樣全綠**（我用 plugin 換走 `_sample_key` 驗過，冇改 repo 檔案）。
   兩邊 bound param type 亦一樣（SQLAlchemy 由 literal 推出 `String`）：

   | | expr type | `.in_()` bind type |
   |---|---|---|
   | 無 cast | `NullType()` | String |
   | 有 cast | `String()` | String |

**影響**：`cast()` **應該保留**（後面講），但個理由錯咗會產生兩種相反嘅壞結果——
下一個人信咗，就會以為呢個 cast 係唯一擋住「變咗加數」嘅嘢而唔敢碰；
或者下一個人發現理由係假嘅，就順手拎走，而拎走之後 expression 由 `String()` 退返 `NullType()`，
以後對 SQLite `||` 嘅隱式 text coercion 有依賴而冇任何文字講清楚。
本 repo 上一輪 review（§508）已經明確講過呢一類「so it must be X」式斷言要當數字咁核實。

**方案 A（推薦）**：保留 `cast()`，改寫理由講返真嘅——cast 唔係防止加數，
係令個 expression 嘅 type 由 `NullType` 變 `String`，令「呢度做緊 text concatenation」
寫喺 SQL 同 SQLAlchemy type 上，而唔係靠 SQLite `||` 嘅隱式 coercion；
同時明講 Python 側同 SQL 側對 position 嘅字串化必須一致。

```python
def _sample_key(numbered) -> ColumnElement:
    """Return the expression naming a row of *numbered* as ``position:activity_id``.

    One value per row, so the whole batch can be selected by a single ``IN``
    against the keys :func:`_sample_filter` builds in Python, which is what
    keeps the predicate the same size at any batch width (CUI-0019).

    The cast is explicitness rather than necessity. ``numbered.c.position`` is
    a label over ``row_number() OVER (...) - 1``, which SQLAlchemy types as
    ``NullType``, and SQLite's ``||`` would coerce it to text on its own; the
    cast is what makes the expression say so, and types it ``String`` rather
    than leaving the ``IN`` bound against an untyped column. What the keys do
    depend on is that both sides render a position the same way: Python's
    ``str(int)`` and SQLite's ``CAST(... AS VARCHAR)`` agree on every integer,
    which is why :func:`_even_positions` must keep returning ``int``.
    """
```

**方案 B**：拎走 `cast()`，`_sample_key` 變 `numbered.c.position.concat(...)`，
docstring 直接講「SQLite `||` 會 coerce integer 成 text」。少一個 SQL 節點、少一個概念，
但 expression 變返 `NullType`，而且 SQL 文字上睇唔出係 text 運算。

**推薦：方案 A。** Cast 本身有價值（type 上講清楚意圖），只係理由要寫返真嘅；
方案 B 拎走嘅嘢比慳到嘅多。改動約 12 行 docstring，零代碼、零測試改動。

### 🟡 W-026 — 「position 行先先 injective」呢個論據係假嘅（docstring + commit message + ticket 三處）

**位置**：
- `src/api/service.py:196-203`（`SAMPLE_KEY_SEPARATOR` docstring）
- `f57caa8` commit message 第 3 段
- `.tickets/in-progress/0001-0200/CUI-0019.md` §解決方案「點解 position 行先」

```
Put the id first instead and an id holding this character would make two
different rows share a key -- which is why the order is the load-bearing half
of this and the character is not.
```

**描述**：**結論（key injective）係啱嘅，理由係錯嘅。**

`key = activity_id + ":" + str(position)` **一樣 injective**：`str(position)` 唔含 `":"`，
所以 key 入面**最後一個** `":"` 必然係我哋插入嗰個，一樣可以唯一切返兩橛。
Position-first 靠「第一個 `":"`」，id-first 靠「最後一個 `":"`」，兩者對稱。
而且呢度**根本冇任何地方 parse 返個 key**——只係 `IN` 做 exact equality，
所以真正需要嘅性質只係 injectivity。

Brute-force 驗證（14 個含 `":"` / 空字串 / 前導零嘅 id × 132 個 position = 1,848 行）：

```
position-first: 1848 keys from 1848 rows, collisions=0
id-first:       1848 keys from 1848 rows, collisions=0
```

**真正承重嘅係：兩個 component 之中，必須有一個嘅 rendering 保證唔含分隔符**
（呢度係 position，因為佢係整數十進制）。次序唔係承重嗰半。

**影響**：
1. 呢句係成個設計選擇嘅核心理由，寫喺三個地方，將來會被引用。
2. 更實際嘅風險：佢將注意力放咗喺**冇所謂嘅嘢**（次序）而**冇寫低真正會爆嘅嘢**
   （position 嘅 rendering 一旦含分隔符、或者 Python / SQL 兩邊 rendering 分家，
   key 就會靜靜雞 match 唔到，而唔係報錯）。下一個人跟住呢句改嘢，
   會守錯咗 invariant。
3. 同科先例：W-020 就係 docstring 自稱係 worst case 但實測唔係，判 🟡。

**方案 A（推薦）**：改寫 docstring，講返真嘅承重條件，同時保留 position-first
（無需改代碼——position-first 冇錯，只係唔比 id-first 優越）：

```python
SAMPLE_KEY_SEPARATOR = ":"
"""Separator joining a position to an activity id in the sample key.

What makes the key injective is that one of its two halves cannot contain this
character: a position is a run of decimal digits, so whichever end it sits at
is unambiguous, and the whole of the other half is the activity id however many
separators that id holds. Putting the position first fixes that end as the
first separator rather than the last, which is a readability choice; both
orders are injective for the same reason, and neither depends on the character
chosen. What the key does depend on is that a position never renders with this
character in it -- see :func:`_sample_key`.
"""
```

**方案 B**：保留現有文字但改成 hedged 講法（「position first so the *first* separator ends it」，
刪走關於 id-first 嘅斷言）。改動最細，但少咗講明真正嘅 invariant。

**推薦：方案 A。** 順帶喺 ticket `CUI-0019.md` §解決方案同步更正（commit message 已入史，
喺 ticket 加一句更正註腳即可，唔使 rewrite history）。

### `src/api/service.py` — W-025

```python
def _sample_key(numbered) -> ColumnElement:
    """Return the expression naming a row of *numbered* as ``position:activity_id``.

    One value per row, so the whole batch can be selected by a single ``IN``
    against the keys :func:`_sample_filter` builds in Python, which is what
    keeps the predicate the same size at any batch width (CUI-0019).

    The cast is explicitness rather than necessity. ``numbered.c.position`` is
    a label over ``row_number() OVER (...) - 1``, which SQLAlchemy types as
    ``NullType``, and SQLite's ``||`` would coerce it to text on its own -- the
    statement renders the same either way. What the cast buys is that the
    expression says it is text and is typed ``String`` rather than leaving the
    ``IN`` bound against an untyped column. What the keys really depend on is
    that both sides render a position identically: Python's ``str(int)`` and
    SQLite's ``CAST(... AS VARCHAR)`` agree on every integer, which is why
    :func:`_even_positions` must keep returning ``int`` -- a float would thin
    the wrong rows silently rather than raise.
    """
    return (
        cast(numbered.c.position, String)
        .concat(SAMPLE_KEY_SEPARATOR)
        .concat(numbered.c.activity_id)
    )
```
