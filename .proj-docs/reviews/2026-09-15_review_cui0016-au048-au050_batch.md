## 審查項 2 — VDBE step proxy 是否穩定

### ✅ 同一 build 內：完全確定性（比佢申報嘅仲好）

8 次獨立 fresh-engine run，step 數 **每次完全相同**：


Developer 申報「約 2.15」「margin 43%」「control 1.00」—— **三個全部準確**。

**首次連線 setup 變異**：我量到 **121 steps**（fresh engine 第一次讀 46300，之後 46179）—— 同佢申報嘅 121 一致。佢講 0.13%，我量到係 narrow read 嘅 **0.26%**；差異無關痛癢，而且**方向係保守嘅**：呢 121 steps 落喺 **narrow 分母**，會**拉低**量到嘅 ratio，令 assertion **更難**通過，唔係更易。

### ✅ 跨 SQLite build：風險低，而且可診斷

本機 SQLite **3.45.1**。跨 build opcode 數一定會變，但呢個 ratio 嘅機制係**結構性**嘅：

- 每條 track，narrow 同 wide 嘅 subquery **都係掃 60 行**（per-track 掃描行數係常數）。
- 唯一變數係每行要評估幾多條 arm：narrow 8 條、wide 64 條 → **per-track arm evaluation 差 8 倍**。
- 量到 2.15 而唔係 8，係因為 `row_number` subquery + `ORDER BY` 呢啲線性成分溝淡咗 —— docstring 有講明（「a square would be 8x here」），**準確**。

SQLite 嘅 OR-optimization（將 `a=1 OR a=2` 轉成多次 index 查找）**結構上用唔到呢度**：predicate 係行喺一個帶 window function 嘅 subquery 之上，window function 阻止 flattening，而 materialised subquery 冇 index。所以個 disjunction 唔會被優化走。

要令 ratio 跌穿 1.5，線性成分要相對 disjunction 大 **2.2 倍**。理論上可能（例如某 build 令 window function 貴好多），實際機會低。**而且就算真係跌穿，個 cause assertion（`_or_arms == width`）仍然會綠，即刻話你知係 cost model 變咗而唔係結構變咗。** 呢個「分開釘 cause 同 consequence」嘅設計，正正令一個 build 引起嘅紅**可診斷而唔係神秘**。

**判定：proxy 成立，遠勝 wall clock，接受。**

### ✅ 三條 assertion 有冇真係分離兩個因素？——有，而且比佢自己講嘅更乾淨

| assertion | 作用 |
|---|---|
| ① `_or_arms(sql) == width` | **cause**：predicate 闊度 == batch 闊度，結構性釘死 |
| ② per-track steps ratio > 1.5 | **consequence** |

- **方案 A**：喺 `BATCH_COST_GROWTH_FLOOR` docstring 加兩句 ——（i）「呢條 test 預期喺 CUI-0019 修好之後變紅；正確反應係改 `MAX_TRACK_FIELDS_PER_REQUEST` 嗰段 docstring，**唔係**調低呢個 floor」；（ii）講明 assertion 門檻係 1.5 而唔係 1.0。**推薦。**
- **方案 B**：順便記低 2.15 係喺邊個 SQLite build 量到（本機 3.45.1）。符合本 repo「每個量度數字都有出處」嘅慣例，亦令將來有人見到 ratio 漂移時分得清係 build 變咗定 code 變咗。**建議連 A 一齊做**（一行）。

## 審查項 4 — 超範圍改動（`60x` → `38x, of this fixture`）：**正當，保留**

- Brief 只叫加 scale caveat，佢連上面兩段嗰句 production 結論都改埋。

- **可剝走性**：係 `schema.py` 嘅第二個 hunk，自足，docstring-only，`git revert` 該 hunk 零副作用 —— 佢申報得準確。
- **而且佢主動申報咗。** 呢個係正確做法。

**判定：保留。剝走反而會令 docstring 自相矛盾。**
