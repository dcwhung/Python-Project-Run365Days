### 4.1 兩個活住嘅 mutant（`src/api/schema.py` 100% line coverage 之下）

方法按 `CLAUDE.md` §6 嘅 mutation-testing 條目做：清 `__pycache__` → 改源碼 → **先用獨立 oracle assert mutant 真係生效** → 再跑 suite。

**Mutant 1：`REFUSAL_LOG_LEVEL = logging.WARNING`**

- Oracle 確認生效：`logging.getLevelName(REFUSAL_LOG_LEVEL)` → `WARNING`
- 後果：CUI-0029 賣嘅頭號性質破咗——Vercel 預設 config 下每個 refusal 由 **0 bytes 變返 553 bytes**
- **418 條 pytest 全部照樣綠**

原因：`test_a_budget_refusal_is_not_logged_as_a_server_fault` 唯一嘅 level 斷言係
`assert REFUSAL_LOG_LEVEL < logging.ERROR` —— `WARNING` 滿足佢。而 docstring 自己寫明「`logging`'s default threshold is `WARNING`… therefore drops these records entirely」，即係話**呢句量度出嚟嘅結論冇任何斷言釘住**。一行修復：`assert REFUSAL_LOG_LEVEL < logging.WARNING`。

**Mutant 2：`super().process_errors(errors, …)` 代替 `super().process_errors(faults, …)`**

- Oracle 確認生效：同一個 operation 由 1 INFO + 1 ERROR 變成 1 INFO + **2** ERROR，其中一個 ERROR 就係 budget refusal 本身
- **418 條 pytest 全部照樣綠**（`tests/test_api.py` 159 條亦全綠）

原因：現有三條 logging 測試分別係「全部係 refusal」同「全部係 fault」。**冇一條 operation 同時帶住一個 refusal 同一個 fault**——而 `faults` vs `errors` 只喺呢種混合 operation 先分得出。`RefusalAwareSchema` docstring 自己就寫「classifying one kind and quietly taking the rest with it is a one-line mistake that no budget test would notice」，諷刺係佢自己個 filter 參數就冇被守住。

我寫咗嗰條 edge case（可直接抄去做補測）：

```
{ a1: activity(id: "7264441638") { t0…t10: track(points: 1000) { sec } }
  a2: activity(id: "BOOM") { id } }      # service.activity monkeypatched 掟 RuntimeError(MARKER)
```

真實結果（未 mutate）：client 見到 2 個 error；log 見到 **1 個 INFO record（refusal，無 exc_info）+ 1 個 ERROR record（fault，exc_info 係 MARKER）**——即係正確行為。Mutate 之後 refusal 會多出一個 ERROR record。

### CUI-0039 — 冇任何測試行過「同一個 operation 同時帶 refusal 同 fault」，令 `process_errors` 個 filter 參數係活 mutant

- **類型**：test-gap
- **優先級**：🟡 Medium
- **來源**：QA Report 2026-09-16（CUI-0029 batch，§4.1 mutant 2）
- **負責人**：Backend Developer
- **相關**：CUI-0029

**問題描述**

`RefusalAwareSchema.process_errors` 把 errors 分成兩堆，只把 `faults` 交返 `super()`：

```python
if faults:
    super().process_errors(faults, execution_context)
```

現有三條 logging 測試分別覆蓋「全部係 refusal」（`test_a_budget_refusal_is_not_logged_as_a_server_fault`）同「全部係 fault」（`test_an_unexpected_resolver_error_is_still_logged_as_a_server_fault`、`test_an_unseeded_budget_still_logs_its_traceback`）。兩種情況下 `faults` 同 `errors` 表現一樣（前者 `faults` 空、`if faults` 唔行；後者 `faults == errors`）。**只有混合 operation 先分得出。**

`RefusalAwareSchema` 自己個 docstring 就寫「classifying one kind and quietly taking the rest with it is a one-line mistake that no budget test would notice」——但守住嗰個 mistake 嘅參數自己冇被守。

**實測（2026-09-16，in-process mutation，清 `__pycache__`）**

```
oracle: 同一 operation 由 1 INFO + 1 ERROR  ->  1 INFO + 2 ERROR
        （多出嗰個 ERROR 就係 budget refusal 本身，連 exc_info）
pytest tests -q          -> 418 passed      ← 冇一條掛
pytest tests/test_api.py -> 159 passed      ← 冇一條掛
```

**建議補測（QA 已行通，可直接抄）**

```python

):
    # faults vs errors: 呢個係唯一分得出兩者嘅 shape。全 refusal 嘅 operation
    # 唔會行到 super()，全 fault 嘅 operation 兩個 list 一樣，所以兩邊都殺唔到
    # 「把未過濾 list 交返 super()」呢個 mutant。
    real = service.activity

    def selective(session, activity_id):
        if activity_id == "BOOM":
            raise _ResolverFaultError("the database went away")
        return real(session, activity_id)

    monkeypatch.setattr(service, "activity", selective)
    document = (
        '{ a1: activity(id: "…") { '
        + " ".join(f"t{i}: track(points: 1000) {{ sec }}" for i in range(11))
        + ' } a2: activity(id: "BOOM") { id } }'
    )
    with caplog.at_level(logging.DEBUG, logger="strawberry.execution"):
        errors = gql_errors(year_client, document)

    assert len(errors) == 2, "the client must still be told both things"
    records = _strawberry_records(caplog)
    refusals = [r for r in records if r.levelno == REFUSAL_LOG_LEVEL]
    faults = [r for r in records if r.levelno == logging.ERROR]
    assert len(refusals) == 1 and refusals[0].exc_info is None
    assert len(faults) == 1 and issubclass(faults[0].exc_info[0], _ResolverFaultError)
    # 最關鍵嗰句：refusal 冇跟住 fault 一齊上 ERROR
    assert not any("budget exhausted" in str(r.msg) for r in faults)
```

QA 已用真 Flask app 行過呢個 shape（未 mutate）：client 見 2 個 error、log 見 1 INFO（refusal，無 exc_info）+ 1 ERROR（fault，exc_info 帶住 marker），即正確行為。

**驗證方式**

- `super().process_errors(errors, …)` → 新測試**必須紅**
- 還原 → 綠
- 全 suite 綠、`api/schema.py` coverage 維持 100%

### CUI-0040 — `service.tracks()` 收到負數 `points` 靜靜回 1 行，同 CUI-0033(a) 立嘅原則相反

- **類型**：tech-debt / robustness
- **優先級**：🟢 Low
- **來源**：QA Report 2026-09-16（CUI-0029 batch，§4 edge case E2）
- **負責人**：Backend Developer
- **相關**：CUI-0033（本票係佢個原則嘅延伸）
- **注意**：**兩個 shipped client 都到唔到**——`schema._track_points` 同 `static/source.ts` 嘅 `checkPoints` 都會先擋

**問題描述**

CUI-0033 (a) 嘅論證係：「`MAX_TRACK_POINTS` 唔可以淨係 bound 個問題，要 bound 埋個答案」——即 service 層唔應該假設 caller 幫佢守住。但同一個 function 對負數 `points` 仍然完全信 caller。

**實測（2026-09-16，真 `run365.db` + 一條 1250 行 synthetic track，只 flush 唔 commit）**

| `points` | `len(tracks(s, ["QA-EDGE"], points)["QA-EDGE"])` |
|---|---|
| `None` | 1000 ← 上限，正確 |
| `0` | 1000 ← falsy → 上限，正確 |
| `False` | 1000 ← 正確 |
| **`-5`** | **1** ← ⚠️ 靜靜回 1 行，唔 raise 唔 clamp |
| `1` | 1 |
| `1000` | 1000 |
| `1001` | 1000 ← `min()` cap，正確 |
| `10**9` | 1000 ← 正確 |

未知 id 一律回 `{'nope': []}`，三個值都一致 ✅。

`min(points, MAX_TRACK_POINTS)` 對 `-5` 回 `-5`，再交去 `_even_positions(1250, -5)`，結果係 1 行——同 `points=1` 撞埋一齊，client 分唔出「我問咗負數」同「我問咗 1」。

**影響**

低。兩個 shipped client 都守住咗，所以今日到唔到。但：
1. `tracks()` 個 docstring 寫「`points`: Samples per track, or `None`/`0` for every stored row up to `MAX_TRACK_POINTS`」——完全冇講負數
2. CUI-0033 (a) 嘅整個理由就係「唔好靠 caller 守」，呢度係同一類遺留
3. 將來任何新 caller（另一個 CLI、另一個 mode、一條 script）都會踩

**建議**

`tracks()` 開頭 clamp 或 raise。Clamp 較簡單同 `min()` 一致：

```python
sample = min(points, MAX_TRACK_POINTS) if points and points > 0 else MAX_TRACK_POINTS
```

⚠️ 但咁樣 `-5` 就變成 1000（「當冇講」），同 `points=0` 一樣。另一個選擇係 raise `ValueError`，同 `_track_points` 措辭一致。**由 developer 揀，但要喺 docstring 講明揀咗邊個**，因為 `0` 同 `-5` 兩個 falsy/negative 嘅語意分別就係 CUI-0025 當初拗過嗰樣嘢。

**驗證方式**

- 對住一條 > 1000 行嘅 synthetic track 逐個值重量上表，`-5` 行為變成揀定嗰個
- `_even_positions` 相關測試維持綠
- 兩個 client 嘅行為零改動（`schema._track_points` / `checkPoints` 仍然先擋，所以 GraphQL 同 static 兩邊嘅 message 唔可以變）
- 全 suite 綠
